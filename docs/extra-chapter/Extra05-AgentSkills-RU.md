# Agent Skills и MCP: две парадигмы расширения возможностей агентов

## Введение: что нужно после MCP?

В главе 10 мы подробно рассмотрели, как MCP (Model Context Protocol) решает проблему подключения агентов к внешним инструментам через стандартизированный протокол. Вы уже научились разрешать агентам обращаться через MCP к базам данных, файловым системам, API-сервисам и другим ресурсам. Давайте вспомним типичный сценарий использования MCP:

```python
from hello_agents import ReActAgent, HelloAgentsLLM
from hello_agents.tools import MCPTool

llm = HelloAgentsLLM()
agent = ReActAgent(name="Ассистент по анализу данных", llm=llm)

# Подключение к MCP-серверу базы данных
db_mcp = MCPTool(server_command=["python", "database_mcp_server.py"])
agent.add_tool(db_mcp)

# Теперь агент может обращаться к базе данных
response = agent.run("Запросить топ-10 сотрудников с наивысшей зарплатой из таблицы employees")
```

Этот код работает хорошо — агент успешно подключается к базе данных. Но при попытке решить более сложные задачи вы столкнётесь с некоторыми тонкими проблемами:

```python
# Более сложное требование
response = agent.run("""
Проанализируй, кто в компании обладает наибольшим влиянием?
Необходимо учесть:
1. Уровень управления и количество подчинённых
2. Уровень зарплаты и темп её роста
3. Стаж работы и стабильность
4. Влияние между отделами
""")
```

Эта задача требует нескольких последовательных запросов к базе данных, где результат каждого запроса влияет на стратегию следующего. Ключевым является то, что агенту нужны **доменные знания**: понимать, как измерять «влияние», с каких точек зрения анализировать данные, как объединить результаты нескольких запросов для получения вывода.



При этом возникают две фундаментальные проблемы:

**Первая проблема — взрыв контекста.** Чтобы агент мог гибко запрашивать базу данных, MCP-серверы обычно предоставляют десятки или даже сотни инструментов (разные таблицы, разные методы запросов). Полные JSON Schema всех этих инструментов загружаются в системный промпт сразу при установке соединения — это может занимать десятки тысяч токенов. По отзывам разработчиков сообщества, только загрузка одного MCP-сервера Playwright занимает 8% окна контекста объёмом 200k токенов, что в ходе многоходового диалога быстро накапливается, приводя к росту затрат и снижению качества рассуждений.

**Вторая проблема — разрыв в возможностях.** MCP решает проблему «может подключиться», но не решает проблему «знает, как использовать». Наличие доступа к базе данных не означает, что агент умеет писать эффективный и безопасный SQL; доступ к файловой системе не означает, что он понимает структуру кода конкретного проекта и принятые стандарты разработки. Это всё равно что дать начинающему программисту доступ ко всем системам, не предоставив руководство по эксплуатации и лучшие практики.

Именно эту ключевую проблему и призваны решить **Agent Skills**. В начале 2025 года Anthropic, развивая идеи MCP, предложила концепцию Agent Skills, которая вызвала широкий отклик в отрасли. Один из разработчиков написал: «Skills и MCP — это разные вещи: Skills — это доменные знания, которые говорят модели, как поступать, и по сути являются продвинутым промптом; а MCP подключает внешние инструменты и данные». Другие считают: «От Function Call к Tool Call, затем к MCP и Skills — суть практически не меняется, это лишь эволюция инженерных практик и форм представления».

Так что же такое Agent Skills? В чём их принципиальное отличие от MCP? Являются ли они конкурентами или взаимодополняют друг друга? В этой главе мы подробно разберём эти вопросы.



## Что такое Agent Skills?

### Ключевая идея проектирования

**Agent Skills — это стандартизированный формат упаковки процедурных знаний.** Если MCP даёт агенту «руки» для работы с инструментами, то Skills предоставляют «руководство по эксплуатации» или «СОП (стандартную операционную процедуру)», которые учат агента правильно использовать эти инструменты.

Эта идея проектирования основана на простом, но глубоком наблюдении: **связность (Connectivity) и возможности (Capability) должны быть разделены.** MCP сосредоточен на первом, Skills — на втором. Такое разделение ответственности даёт чёткие архитектурные преимущества:

- **Зона ответственности MCP**: предоставить стандартизированный интерфейс доступа, чтобы агент мог «дотянуться» до данных и инструментов внешнего мира.
- **Зона ответственности Skills**: предоставить доменную экспертизу — рассказать агенту, как именно «комбинировать эти инструменты» в конкретном сценарии.

Хорошая аналогия: MCP — это как USB-интерфейс или драйвер устройства, определяющий способ подключения; а Skills — это как программное приложение, определяющее, как использовать подключённое устройство для выполнения конкретных задач. У вас может быть превосходный драйвер принтера (MCP), но без инструкции о том, как настроить поля страниц и двустороннюю печать в Word (Skill), вы всё равно не сможете эффективно выполнить задачу.

### Прогрессивное раскрытие: решение проблемы контекста

Ключевое новшество Agent Skills — это механизм **прогрессивного раскрытия (Progressive Disclosure)**. Этот механизм разделяет информацию о навыке на три уровня, которые агент загружает по мере необходимости: это гарантирует, что детали будут доступны при необходимости, и при этом избавляет от необходимости загружать всё сразу в окно контекста.

#### Первый уровень: метаданные (Metadata)

В архитектуре Skills каждый навык хранится в отдельной папке, центральным элементом которой является Markdown-файл с именем `SKILL.md`. Этот файл должен начинаться с блока YAML Frontmatter, содержащего базовую информацию о навыке.

При запуске агент сканирует все установленные папки навыков и **читает только часть Frontmatter каждого файла `SKILL.md`**, загружая эти метаданные в системный промпт. По данным практических измерений, метаданные одного навыка занимают около **100 токенов**. Даже при наличии 50 установленных навыков начальное потребление контекста составит всего около 5000 токенов.

Это разительно контрастирует со способом работы MCP. В типичной реализации MCP клиент при подключении к серверу запрашивает полные JSON Schema всех доступных инструментов через запрос `tools/list`, что может немедленно занять десятки тысяч токенов.

#### Второй уровень: основное тело навыка (Instructions)

Когда агент анализирует запрос пользователя и определяет, что данный навык тесно связан с текущей задачей, происходит загрузка второго уровня. Агент читает полное содержимое файла `SKILL.md` и загружает в контекст подробные инструкции, примечания и примеры.

На этом этапе агент получает весь необходимый контекст для выполнения задачи: структуру базы данных, шаблоны запросов, предупреждения и т.д. Потребление токенов на этом уровне зависит от сложности инструкций и обычно составляет от 1000 до 5000 токенов.

#### Третий уровень: дополнительные ресурсы (Scripts & References)

Для более сложных навыков `SKILL.md` может ссылаться на другие файлы в той же папке: скрипты, файлы конфигурации, справочные документы. Агент **загружает эти ресурсы только тогда, когда они действительно нужны**.

Например, файловая структура навыка для работы с PDF может выглядеть так:

```
skills/pdf-processing/
├── SKILL.md              # Основной файл навыка
├── parse_pdf.py          # Скрипт разбора PDF
├── forms.md              # Руководство по заполнению форм (загружается только при задачах с формами)
└── templates/            # Шаблоны PDF
    ├── invoice.pdf
    └── report.pdf
```

В файле `SKILL.md` ссылки на дополнительные ресурсы используются следующим образом:

- Когда нужно выполнить разбор PDF, агент запускает скрипт `parse_pdf.py`
- Когда встречается задача заполнения формы, загружается `forms.md` с подробными инструкциями
- Файлы шаблонов используются только при необходимости создать документ определённого формата

Такая конструкция имеет два ключевых преимущества:

1. **Неограниченный объём знаний**: благодаря скриптам и внешним файлам навык может «нести» знания, превышающие лимиты контекста. Например, навык анализа данных может содержать файл данных объёмом 1 ГБ и скрипт запросов — агент обращается к данным через скрипт, не загружая весь датасет в контекст.

2. **Детерминированное выполнение**: сложные вычисления, преобразование данных, разбор форматов — всё это передаётся на исполнение коду, что устраняет недетерминированность и проблему галлюцинаций при генерации LLM.

### Эффект прогрессивного раскрытия: от 16k до 500 токенов

Практические случаи из сообщества разработчиков наглядно демонстрируют силу прогрессивного раскрытия. В одном реальном сценарии:

- **Традиционный подход через MCP**: прямое подключение к MCP-серверу с большим количеством определений инструментов — начальная загрузка занимает **16 000 токенов**
- **С обёрткой в виде Skill**: создаётся простой навык-«шлюз», в Frontmatter описывается только функциональность — начальное потребление составляет всего **500 токенов**

Когда агент определяет, что навык нужен, он загружает подробные инструкции и по мере необходимости вызывает нижележащие инструменты MCP. Такая архитектура не только существенно снижает начальные затраты, но и делает управление контекстом в процессе диалога более точным и эффективным.

### Различия с точки зрения инженерии

Рассмотрим конкретный пример: вы создаёте агента для помощи команде в проведении ревью кода.

**Зона ответственности MCP**:

```python
# MCP обеспечивает стандартизированный доступ к GitHub
github_mcp = MCPTool(server_command=["npx", "-y", "@modelcontextprotocol/server-github"])

# Инструменты, предоставляемые MCP (упрощённый пример):
# - list_pull_requests(repo, state)
# - get_pull_request_details(pr_number)
# - list_pr_comments(pr_number)
# - create_pr_comment(pr_number, body)
# - get_file_content(repo, path, ref)
# - list_pr_files(pr_number)
```

MCP даёт агенту возможность «обращаться» к GitHub и вызывать эти API. Но он не знает, что именно «нужно» делать.

**Зона ответственности Skills**:

```markdown
---
name: code-review-workflow
description: Выполняет стандартный процесс ревью кода: проверка стиля, проблем безопасности, покрытия тестами и т.д.
---

# Рабочий процесс ревью кода

## Чеклист ревью

При проведении ревью кода выполните следующие шаги:

1. **Получить информацию о PR**: вызвать `get_pull_request_details` для понимания контекста изменений
2. **Проанализировать изменённые файлы**: вызвать `list_pr_files` для получения списка файлов
3. **Поочерёдно проверить каждый файл**:
   - Для файлов `.py`: проверить соответствие PEP 8, наличие очевидных проблем с производительностью
   - Для файлов `.js/.ts`: проверить необработанные Promise, использование устаревших API
   - Для тестовых файлов: убедиться, что новые ветки кода охвачены тестами
4. **Проверка безопасности**:
   - Нет ли жёстко закодированных секретов (ключи, пароли)?
   - Нет ли риска SQL-инъекций или XSS?
5. **Предоставить обратную связь**:
   - Критические проблемы: прокомментировать напрямую через `create_pr_comment`
   - Предложения по улучшению: указать в итоговом резюме

## Внутренние стандарты компании

- Все запросы к БД должны использовать параметризованные запросы
- Конечные точки API должны иметь декоратор проверки прав доступа
- Новая функциональность должна сопровождаться юнит-тестами (покрытие > 80%)

### Взаимодополнение, а не конкуренция: гибридная архитектура Skills + MCP

Поняв различия между двумя подходами, мы убеждаемся: **Skills и MCP — не конкуренты, а взаимодополняющие технологии**. Наилучшая практика — объединить их, создав многоуровневую архитектуру:

**Типовой рабочий процесс**:

1. Пользователь спрашивает: «Кто в компании обладает наибольшим влиянием?»
2. **Уровень Skills** определяет, что это задача анализа данных, и загружает навык `mysql-employees-analysis`
3. **Уровень Skills** в соответствии с инструкциями навыка разбивает задачу на подзадачи: запрос управленческих связей, сравнение зарплат, стаж работы и т.д.
4. **Уровень MCP** выполняет конкретные SQL-запросы и возвращает результаты
5. **Уровень Skills** опираясь на доменные знания навыка, интерпретирует данные и формирует комплексный анализ
6. Структурированный ответ возвращается пользователю

Преимущества такой архитектуры:

- **Разделение ответственности**: MCP отвечает за «возможности», Skills — за «мудрость»
- **Оптимизация затрат**: прогрессивная загрузка существенно снижает потребление токенов
- **Удобство сопровождения**: бизнес-логика (Skills) отделена от инфраструктуры (MCP)
- **Повторное использование**: один MCP-сервер может использоваться несколькими навыками

## Техническая реализация: создание и использование Skills

### Детальное описание спецификации SKILL.md

Рассмотрим подробнее стандартную структуру файла `SKILL.md`:

```markdown
---
# === Обязательные поля ===
name: skill-name
  # Уникальный идентификатор навыка, в формате kebab-case

description: >
  Краткое, но точное описание:
  1. Что делает этот навык
  2. Когда следует его использовать
  3. В чём его ключевая ценность
  # Важно: description — единственная основа для выбора навыка агентом, пишите ясно!

# === Необязательные поля ===
version: 1.0.0
  # Семантическая версия

allowed_tools: [tool1, tool2]
  # Белый список инструментов, которые может вызывать данный навык

required_context: [context_item1]
  # Контекстная информация, необходимая для навыка

license: MIT
  # Лицензия

author: Your Name <email@example.com>
  # Информация об авторе

tags: [database, analysis, sql]
  # Теги для категоризации и поиска
---

# Заголовок навыка

## Обзор
(Подробное описание навыка: сценарии использования, технический контекст и т.д.)

## Предварительные условия
(Конфигурация окружения, зависимости и т.д., необходимые для работы навыка)

## Рабочий процесс
(Детальное описание шагов, которые агент должен выполнить)

## Лучшие практики
(Извлечённые уроки, предупреждения, типичные ловушки)

## Примеры
(Конкретные случаи использования для понимания навыка агентом)

## Устранение неполадок
(Частые проблемы и их решения)
```

### Принципы написания качественных Skills

По официальной документации Anthropic и лучшим практикам сообщества, для создания эффективных Skills нужно соблюдать следующие принципы:

#### 1. Точное описание (Description)

Поле `description` — ключевой элемент для принятия решений агентом. Оно должно:

- **Точно определять область применения**: избегать расплывчатых описаний типа «помогает обрабатывать данные»
- **Содержать ключевые слова для срабатывания**: позволять агенту соотносить намерения пользователя с навыком
- **Указывать уникальную ценность**: отличаться от других навыков

❌ **Плохое описание**:
```yaml
description: Обрабатывает запросы к базе данных
```

✅ **Хорошее описание**:
```yaml
description: >
  Преобразует бизнес-вопросы на естественном языке в SQL-запросы и анализирует
  данные в примере базы данных MySQL employees.
  Подходит для запросов информации о сотрудниках, статистики зарплат,
  анализа отделов, истории изменения должностей и т.д.
  Использовать, когда пользователь задаёт вопросы о сотрудниках, зарплатах или отделах.
```

#### 2. Модульность и единственная ответственность

Один Skill должен быть сосредоточен на одной чёткой области или типе задачи. Если навык пытается делать слишком много, это приводит к:

- Слишком широкому описанию, снижающему точность соответствия
- Слишком длинному содержанию инструкций, расходующему контекст
- Сложности в сопровождении и обновлении

**Рекомендация**: вместо одного «универсального навыка анализа данных» создавайте несколько специализированных:
- `mysql-employees-analysis`: только для анализа базы данных employees
- `sales-data-analysis`: только для анализа данных о продажах
- `user-behavior-analysis`: только для анализа поведения пользователей

#### 3. Принцип детерминированности

Для сложных задач, требующих точного выполнения, предпочтительно использовать скрипты, а не полагаться на генерацию LLM. Например, при экспорте данных лучше написать специальный скрипт для формирования Excel-файла (вместо того чтобы позволять LLM генерировать бинарное содержимое, что чревато ошибками), а в `SKILL.md` только указать агенту, когда вызывать этот скрипт.

#### 4. Стратегия прогрессивного раскрытия

Грамотно используйте трёхуровневую структуру, распределяя информацию по важности и частоте использования:

- **Основной `SKILL.md`**: основной рабочий процесс, часто используемые шаблоны
- **Дополнительная документация** (например, `advanced.md`): продвинутые сценарии, граничные случаи
- **Файлы данных**: большие справочные данные, доступ к которым организован через скрипты по мере необходимости

### Шаг 1: Понять задачу

Тщательно проанализировать описание на естественном языке, определить:
- **Цель запроса**: какие данные нужны? (сотрудники, зарплаты, отделы...)

## Типовые шаблоны запросов

### Шаблон 1: Запрос базовой информации

```sql
-- Запрос базовой информации о конкретном сотруднике
SELECT emp_no, CONCAT(first_name, ' ', last_name) AS full_name,
       gender, birth_date, hire_date
FROM employees
WHERE emp_no = <номер_сотрудника>;
```

### Шаблон 2: Запрос текущего состояния

```sql
-- Топ-10 сотрудников с наибольшей текущей зарплатой
SELECT e.emp_no,
       CONCAT(e.first_name, ' ', e.last_name) AS name,
       s.salary
FROM employees e
JOIN salaries s ON e.emp_no = s.emp_no
WHERE s.to_date = '9999-01-01'  -- текущая зарплата
ORDER BY s.salary DESC
LIMIT 10;
```

### Шаблон 3: Анализ исторических трендов

```sql
-- История изменения зарплаты конкретного сотрудника
SELECT emp_no, salary, from_date, to_date,
       salary - LAG(salary) OVER (ORDER BY from_date) AS increase
FROM salaries
WHERE emp_no = <номер_сотрудника>
ORDER BY from_date;
```

### Шаблон 4: Запрос с объединением нескольких таблиц

```sql
-- Средняя зарплата по отделам (текущая)
SELECT d.dept_name,
       COUNT(DISTINCT de.emp_no) AS emp_count,
       ROUND(AVG(s.salary), 2) AS avg_salary
FROM departments d
JOIN dept_emp de ON d.dept_no = de.dept_no
JOIN salaries s ON de.emp_no = s.emp_no
WHERE de.to_date = '9999-01-01'  -- текущие сотрудники
  AND s.to_date = '9999-01-01'   -- текущая зарплата
GROUP BY d.dept_name
ORDER BY avg_salary DESC;
```

### Шаблон 5: Сложный бизнес-анализ

```sql
-- Анализ «влияния»: комплексный учёт уровня управления, зарплаты и стажа
WITH manager_hierarchy AS (
    -- Подсчёт подчинённых каждого руководителя
    SELECT dm.emp_no, COUNT(de.emp_no) AS subordinate_count
    FROM dept_manager dm
    JOIN dept_emp de ON dm.dept_no = de.dept_no
    WHERE dm.to_date = '9999-01-01'
      AND de.to_date = '9999-01-01'
      AND de.emp_no != dm.emp_no
    GROUP BY dm.emp_no
),
current_salary AS (
    -- Текущая зарплата
    SELECT emp_no, salary
    FROM salaries
    WHERE to_date = '9999-01-01'
),
tenure AS (
    -- Стаж работы (лет)
    SELECT emp_no,
           TIMESTAMPDIFF(YEAR, hire_date, CURDATE()) AS years_employed
    FROM employees
)
SELECT e.emp_no,
       CONCAT(e.first_name, ' ', e.last_name) AS name,
       COALESCE(mh.subordinate_count, 0) AS team_size,
       cs.salary,
       t.years_employed,
       -- Простая оценка влияния (веса можно настроить)
       (COALESCE(mh.subordinate_count, 0) * 10 +
        cs.salary / 1000 +
        t.years_employed * 5) AS influence_score
FROM employees e
JOIN current_salary cs ON e.emp_no = cs.emp_no
JOIN tenure t ON e.emp_no = t.emp_no
LEFT JOIN manager_hierarchy mh ON e.emp_no = mh.emp_no
WHERE cs.salary > 60000  -- отфильтровать низкооплачиваемых сотрудников
ORDER BY influence_score DESC
LIMIT 20;
```

## Важные замечания

### ⚠️ Правильная обработка полей дат

- **Текущее состояние**: обязательно фильтровать по `to_date = '9999-01-01'`
- **Исторические запросы**: учитывать диапазоны `from_date` и `to_date`
- **Вычисления с датами**: использовать функции `TIMESTAMPDIFF`, `DATEDIFF` и т.д.

### ⚠️ Оптимизация производительности

- **JOIN больших таблиц**: предпочитать индексируемые поля (emp_no, dept_no)
- **Агрегирующие запросы**: разумно использовать GROUP BY и HAVING
- **Ограничение результатов**: для отображаемых запросов добавлять LIMIT
- **Оптимизация подзапросов**: для сложных запросов использовать WITH (CTE) для улучшения читаемости и производительности

### ⚠️ Качество данных

- **Обработка NULL**: использовать COALESCE или IFNULL для обработки пустых значений
- **Дублирующиеся записи**: сотрудник может неоднократно менять отдел — при запросах учитывать дедупликацию
- **Временные границы данных**: база содержит только данные за 1985–2000 годы

### Неизбежность многоуровневой архитектуры

Опираясь на различные точки зрения, можно сделать вывод: **Skills и MCP представляют два неизбежно разделяющихся уровня в архитектуре агентов**. По мере роста сложности агентных систем такое разделение становится неизбежным:

```
Прикладной уровень (Application Layer)
  ↓ Agent Skills
  ↓ Доменные знания, рабочие процессы, лучшие практики

Транспортный уровень (Transport Layer)
  ↓ MCP
  ↓ Стандартизированный интерфейс, вызов инструментов, доступ к ресурсам

Инфраструктурный уровень (Infrastructure Layer)
  ↓ Базы данных, API, файловые системы, внешние сервисы
```

Это в точности повторяет путь эволюции традиционной программной архитектуры (от монолита к многоуровневой архитектуре и к микросервисам) — только применительно к AI-сфере.

### Вызовы и риски

Вместе с тем необходимо учитывать потенциальные риски:

**Вызовы безопасности**:
- Skills содержат исполняемые скрипты — существует риск инъекции кода
- MCP-серверы могут открывать интерфейсы к конфиденциальным данным
- Надёжность сторонних навыков сложно верифицировать

**Загрязнение контекста**:
- По мере роста числа Skills даже метаданные могут занимать значительный объём контекста
- Необходимы более интеллектуальные механизмы индексации и поиска навыков

**Риск фрагментации**:
- Хотя MCP стандартизируется, формат Skills ещё не унифицирован
- Разные вендоры могут выпустить несовместимые спецификации Skills



## Итоги

Agent Skills и MCP представляют два ключевых уровня абстракции в стеке агентных технологий:

- **MCP (Model Context Protocol)**: решает проблему «связности» — это стандартизированный интерфейс взаимодействия агента с внешним миром, аналог «нервной системы» или «рук»
- **Agent Skills**: решают проблему «возможностей» — это упаковка доменных знаний и рабочих процессов, аналог «коры головного мозга» или «операционного руководства»

Они не конкуренты, а взаимодополняющие технологии:

**Ключевые наблюдения**:

1. **Многоуровневая архитектура — неизбежная тенденция**: по мере роста сложности агентных систем разделение «слоя связности» и «слоя знаний» становится неизбежным

2. **Эффективность контекста — ключевое противоречие**: механизм прогрессивного раскрытия Skills снижает потребление токенов более чем на 90% — это главное техническое преимущество

3. **Демократизация доменных знаний**: Skills позволяют не только разработчикам вносить вклад в возможности агентов — это существенно расширит горизонты применения AI

4. **Гибридная архитектура — лучшая практика**: в корпоративных приложениях MCP обеспечивает инфраструктурную связность, Skills — бизнес-логику; только их сочетание позволяет построить эффективную и поддерживаемую агентную систему

**Практические рекомендации**:

- Для **подключения к внешним сервисам** (базы данных, API, облачные сервисы) — используйте MCP
- Для **сложных рабочих процессов** (многошаговые задачи, специализированные доменные знания) — используйте Skills
- В сценариях **с ограниченным контекстом** (длинные диалоги, большое количество инструментов) — применяйте Skills для прогрессивного управления контекстом
- При создании **корпоративных агентов** — используйте многоуровневую архитектуру MCP + Skills

После изучения этой главы вы должны уметь:
- Понимать принципиальное различие и взаимодействие Agent Skills и MCP
- Владеть механизмом прогрессивного раскрытия Skills и его преимуществами
- Писать качественные файлы SKILL.md
- Обоснованно выбирать и сочетать обе технологии в реальных проектах
- Создавать чётко структурированные, эффективные и легко сопровождаемые агентные системы

Агентные технологии продолжают стремительно развиваться. MCP уже стал де-факто стандартом слоя связности, а идеи Skills влияют на всю отрасль. Овладение обеими технологиями поможет вам в эпоху AI создавать более мощные и практичные агентные приложения.
