# Глава 7: Собственный фреймворк агента

В предыдущих главах мы разобрали основы агентов и на практике оценили удобство разработки, которое дают мейнстримные фреймворки. Начиная с этой главы, мы переходим к более сложному и ценному этапу: **построению агентного фреймворка с нуля — HelloAgents**.

Чтобы обеспечить непрерывность и воспроизводимость учебного процесса, HelloAgents будет развиваться через итерации версий. В итоге мы будем использовать этот самодельный фреймворк для эффективной реализации продвинутых кейсов в следующих главах книги.

## 7.1 Общий дизайн архитектуры фреймворка

### 7.1.1 Зачем создавать собственный фреймворк

В современном быстро развивающемся ландшафте агентных технологий на рынке уже существует множество зрелых фреймворков. Зачем же тогда строить новый с нуля?

**(1) Стремительные изменения и ограничения рыночных фреймворков**

Область агентов развивается стремительно, постоянно рождаются новые концепции. У каждого фреймворка своё позиционирование и понимание дизайна агентов, однако ключевые знания об агентах едины.

- **Сложность избыточной абстракции**: Многие фреймворки в погоне за универсальностью вводят многочисленные уровни абстракции и параметры конфигурации. Возьмём LangChain: его механизм цепных вызовов гибок, но имеет крутую кривую обучения для новичков — для выполнения простых задач нередко нужно разобраться в десятках концепций.
- **Нестабильность из-за быстрых итераций**: Коммерческие фреймворки часто меняют API-интерфейсы в погоне за долей рынка. Разработчики регулярно сталкиваются с ситуацией, когда после обновления версии код перестаёт работать, а издержки на поддержку остаются высокими.
- **Логика «чёрного ящика»**: Многие фреймворки слишком плотно инкапсулируют ключевую логику, лишая разработчиков понимания внутренних механизмов агентов и возможностей глубокой кастомизации. При возникновении проблем приходится полагаться только на документацию и поддержку сообщества, а если сообщество недостаточно активно, обратная связь может затянуться на долгое время — это тормозит дальнейшую разработку.
- **Сложность зависимостей**: Зрелые фреймворки тащат за собой большое количество пакетов-зависимостей с крупным размером установки, что при совместной работе с другим кодом проекта может вызывать конфликты зависимостей.

**(2) Качественный скачок: от пользователя к строителю**

Создание собственного агентного фреймворка — это, по сути, процесс трансформации из «пользователя» в «строителя». Ценность этой трансформации долгосрочна.

- **Глубокое понимание принципов работы агентов**: Реализуя каждый компонент своими руками, разработчик по-настоящему понимает мыслительный процесс агента, механизмы вызова инструментов, а также плюсы, минусы и различия разных паттернов проектирования.
- **Полный контроль**: Собственный фреймворк означает полный контроль над каждой строчкой кода — можно точно настраивать систему под конкретные нужды, не будучи ограниченным философией стороннего фреймворка.
- **Развитие навыков системного проектирования**: В процессе построения фреймворка задействуются ключевые навыки программной инженерии: модульное проектирование, абстракция интерфейсов, обработка ошибок — всё это имеет большое значение для долгосрочного роста разработчика.

**(3) Необходимость кастомизации и глубокого освоения**

На практике требования к агентам сильно различаются в зависимости от сценария, и часто требуется вторичная разработка на базе универсальных фреймворков.

- **Оптимизация под конкретные домены**: Вертикальные области — финансы, здравоохранение, образование — часто требуют специализированных шаблонов промптов, особой интеграции инструментов и кастомных стратегий безопасности.
- **Точный контроль производительности и ресурсов**: В промышленных средах предъявляются строгие требования к времени отклика, потреблению памяти и возможностям параллельной обработки. «Универсальные» решения общих фреймворков зачастую не могут удовлетворить точечные потребности.
- **Требования к прозрачности для обучения**: В нашем учебном сценарии учащиеся ожидают чётко видеть каждый шаг процесса создания агента и понимать механизмы работы разных парадигм, что требует от фреймворка высокой наблюдаемости и интерпретируемости.

### 7.1.2 Философия проектирования фреймворка HelloAgents

Создание нового агентного фреймворка — это не вопрос количества функций, а вопрос того, действительно ли философия проектирования решает болевые точки существующих фреймворков. Дизайн HelloAgents вращается вокруг ключевого вопроса: как дать учащимся возможность и быстро начать работу, и глубоко понять принципы работы агентов?

Знакомясь с любым зрелым фреймворком впервые, поначалу восхищаешься богатством функций, но вскоре обнаруживаешь проблему: для выполнения простой задачи нередко нужно разобраться в более чем десятке концепций — Chain, Agent, Tool, Memory, Retriever и т. д. У каждой концепции свой уровень абстракции, что делает кривую обучения крайне крутой. Хотя эта сложность обеспечивает мощную функциональность, она же становится препятствием для начинающих. Фреймворк HelloAgents стремится найти баланс между функциональной полнотой и дружелюбностью к обучению, формулируя четыре ключевые философии проектирования.

**(1) Баланс между лёгкостью и ориентацией на обучение**

Отличный учебный фреймворк должен обладать полной читаемостью. HelloAgents разделяет основной код по главам, опираясь на простой принцип: любой разработчик с базовыми знаниями программирования должен за разумное время полностью понять принципы работы фреймворка. В управлении зависимостями фреймворк придерживается минималистской стратегии: кроме официального SDK OpenAI и нескольких необходимых базовых библиотек, тяжёлые зависимости не вводятся. При возникновении проблем можно напрямую находить код самого фреймворка, не разыскивая ответы в сложных деревьях зависимостей.

**(2) Прагматичный выбор на основе стандартных API**

API OpenAI стал отраслевым стандартом, и практически все ведущие провайдеры LLM активно добиваются совместимости с этим интерфейсом. HelloAgents решает строиться на этом стандарте, а не изобретать абстрактный интерфейс заново. Это решение продиктовано несколькими соображениями. Первое — гарантия совместимости: после освоения HelloAgents при переходе на другие фреймворки или интеграции в существующие проекты базовая логика вызовов API будет полностью идентична. Второе — снижение издержек на обучение: не нужно осваивать новые концептуальные модели, так как все операции основаны на знакомых стандартных интерфейсах.

**(3) Продуманный прогрессивный учебный путь**

HelloAgents предоставляет чёткий учебный путь. Учебный код каждой главы мы сохраняем как историческую версию, которую можно скачать через pip, поэтому не нужно беспокоиться о доступности кода — каждую ключевую функцию вы напишете сами. Такой подход позволяет двигаться вперёд в своём темпе. Каждое обновление органично, без концептуальных скачков и пробелов в понимании. Стоит отметить, что содержание этой главы опирается на материал предыдущих шести глав, и точно так же эта глава закладывает фундамент для изучения продвинутых знаний в последующих главах.

**(4) Единая абстракция «инструмента»: всё есть инструмент**

Для последовательного воплощения философии лёгкости и учебной направленности HelloAgents сделал ключевое упрощение в архитектуре: кроме основного класса Agent, всё остальное — это инструменты (Tools). Модули Memory, RAG (Retrieval-Augmented Generation), RL (Reinforcement Learning), MCP (Protocol) и другие, которые во многих других фреймворках являются самостоятельными концепциями с отдельными уровнями обучения, в HelloAgents единообразно абстрагированы как «инструменты». Замысел этого дизайна — устранить лишние уровни абстракции, позволяя учащимся вернуться к наиболее интуитивной логике «агент вызывает инструменты», тем самым реально достигая единства быстрого старта и глубокого понимания.

## 7.2 Расширение HelloAgentsLLM

Содержание этого раздела — итеративное улучшение `HelloAgentsLLM`, созданного в разделе 4.1.3. Мы превратим этот базовый клиент в более адаптивный хаб вызовов моделей. Улучшение строится вокруг трёх целей:

1. **Поддержка нескольких провайдеров**: Обеспечить плавное переключение между различными ведущими провайдерами LLM-сервисов — OpenAI, ModelScope, Zhipu AI и т. д. — без привязки фреймворка к конкретному вендору.
2. **Интеграция локальных моделей**: Ввести VLLM и Ollama — два высокопроизводительных решения для локального развёртывания — как дополнение производственного уровня к решению на базе Hugging Face Transformers из раздела 3.2.3, удовлетворяя потребности в приватности данных и контроле затрат.
3. **Механизм автоопределения**: Создать механизм автоматического распознавания, позволяющий фреймворку интеллектуально определять тип используемого LLM-сервиса на основе информации из окружения, упрощая процесс конфигурации для пользователя.

### 7.2.1 Поддержка нескольких провайдеров

Ранее определённый класс `HelloAgentsLLM` уже умеет подключаться к любому совместимому с OpenAI сервису через два ключевых параметра: `api_key` и `base_url`. Теоретически это гарантирует универсальность, но на практике у разных провайдеров есть различия в именовании переменных среды, адресах API по умолчанию и рекомендуемых моделях. Если каждый раз при смене провайдера нужно вручную искать и менять код, это сильно снижает эффективность разработки. Чтобы решить эту проблему, мы вводим параметр `provider`. Идея улучшения: пусть `HelloAgentsLLM` сам обрабатывает детали конфигурации разных провайдеров, предоставляя пользователю единый лаконичный интерфейс вызова. Конкретные детали реализации разберём в разделе 7.2.3 «Механизм автоопределения». Здесь сосредоточимся на том, как использовать этот механизм для расширения фреймворка.

Ниже на примере добавления поддержки платформы ModelScope покажем, как расширять `HelloAgentsLLM` через наследование. Надеемся, что читатель научится не только «использовать» фреймворк, но и «расширять» его. Прямое изменение исходного кода установленных библиотек — не рекомендуемая практика, так как она затрудняет последующие обновления библиотеки.

**(1) Создаём кастомный LLM-класс с наследованием**

Предположим, в директории нашего проекта есть файл `my_llm.py`. Сначала импортируем базовый класс `HelloAgentsLLM` из библиотеки `hello_agents`, затем создаём новый класс `MyLLM`, наследующий от него.

```python
# my_llm.py
import os
from typing import Optional
from openai import OpenAI
from hello_agents import HelloAgentsLLM

class MyLLM(HelloAgentsLLM):
    """
    Кастомный LLM-клиент, добавляющий поддержку ModelScope через наследование.
    """
    pass  # Пока оставляем пустым
```

**(2) Переопределяем метод `__init__` для поддержки нового провайдера**

Далее переопределяем метод `__init__` в классе `MyLLM`. Цель: когда пользователь передаёт `provider="modelscope"` — выполнять кастомную логику; в остальных случаях — вызывать исходную логику родительского класса `HelloAgentsLLM`, сохраняя поддержку других встроенных провайдеров (например, OpenAI).

```python
class MyLLM(HelloAgentsLLM):
    def __init__(
        self,
        model: Optional[str] = None,
        api_key: Optional[str] = None,
        base_url: Optional[str] = None,
        provider: Optional[str] = "auto",
        **kwargs
    ):
        # Проверяем, является ли провайдер 'modelscope', который нужно обработать особо
        if provider == "modelscope":
            print("Используем кастомный ModelScope Provider")
            self.provider = "modelscope"

            # Разбираем учётные данные ModelScope
            self.api_key = api_key or os.getenv("MODELSCOPE_API_KEY")
            self.base_url = base_url or "https://api-inference.modelscope.cn/v1/"

            # Проверяем наличие учётных данных
            if not self.api_key:
                raise ValueError("Ключ API ModelScope не найден. Задайте переменную среды MODELSCOPE_API_KEY.")

            # Задаём модель по умолчанию и другие параметры
            self.model = model or os.getenv("LLM_MODEL_ID") or "Qwen/Qwen2.5-VL-72B-Instruct"
            self.temperature = kwargs.get('temperature', 0.7)
            self.max_tokens = kwargs.get('max_tokens')
            self.timeout = kwargs.get('timeout', 60)

            # Создаём экземпляр клиента OpenAI с полученными параметрами
            self._client = OpenAI(api_key=self.api_key, base_url=self.base_url, timeout=self.timeout)

        else:
            # Если не modelscope — передаём управление родительскому классу
            super().__init__(model=model, api_key=api_key, base_url=base_url, provider=provider, **kwargs)
```

Этот код демонстрирует идею «переопределения»: мы перехватываем случай `provider="modelscope"` и обрабатываем его особо. Для всех остальных случаев передаём управление родительскому классу через `super().__init__(...)`, сохраняя весь исходный функционал фреймворка.

**(3) Использование кастомного класса `MyLLM`**

Теперь можно использовать наш класс `MyLLM` в бизнес-логике проекта так же, как нативный `HelloAgentsLLM`.

Сначала настраиваем ключ API ModelScope в файле `.env`:

```bash
# файл .env
MODELSCOPE_API_KEY="your-modelscope-api-key"
```

Затем импортируем и используем `MyLLM` в главном файле программы:

```python
# my_main.py
from dotenv import load_dotenv
from my_llm import MyLLM  # Импортируем свой класс

# Загружаем переменные среды
load_dotenv()

# Создаём экземпляр нашего переопределённого клиента и указываем провайдера
llm = MyLLM(provider="modelscope")

# Подготавливаем сообщения
messages = [{"role": "user", "content": "Привет, представься, пожалуйста."}]

# Делаем вызов; методы think и другие наследуются от родительского класса — переопределять не нужно
response_stream = llm.think(messages)

# Выводим ответ
print("Ответ ModelScope:")
for chunk in response_stream:
    # Chunk уже выводится в my_llm; здесь просто пропускаем
    # print(chunk, end="", flush=True)
    pass
```

Выполнив эти шаги, мы успешно расширили библиотеку `hello-agents` новой функциональностью, не изменяя её исходный код. Этот подход не только обеспечивает чистоту и поддерживаемость кода, но и гарантирует, что кастомный функционал не будет утрачен при обновлении библиотеки в будущем.

### 7.2.2 Вызов локальных моделей

В разделе 3.2.3 мы научились запускать модели с открытым кодом локально с помощью библиотеки Hugging Face Transformers. Этот метод отлично подходит для вводного обучения и функциональной верификации, однако его базовая реализация имеет ограниченную производительность при обработке высоконагруженных запросов и обычно не является первым выбором для промышленных сред.

Для достижения высокопроизводительного, промышленного инференса моделей локально сообщество создало такие отличные инструменты, как VLLM и Ollama. Они значительно повышают пропускную способность и эффективность работы с моделями за счёт таких технологий, как continuous batching и PagedAttention, и оборачивают модели как API-сервисы, совместимые со стандартом OpenAI. Это означает, что мы можем легко интегрировать их в `HelloAgentsLLM`.

**VLLM**

VLLM — высокопроизводительная Python-библиотека для инференса LLM. Благодаря передовым технологиям, таким как PagedAttention, она достигает в несколько раз большей пропускной способности по сравнению со стандартными реализациями Transformers. Ниже — полные шаги для локального развёртывания VLLM-сервиса:

Сначала установите VLLM согласно вашей аппаратной конфигурации (особенно версии CUDA). Рекомендуем следовать [официальной документации](https://docs.vllm.ai/en/latest/getting_started/installation.html) во избежание проблем с несовместимостью версий.

```python
pip install vllm
```

После установки запускаем OpenAI-совместимый API-сервис следующей командой. VLLM автоматически скачает веса указанной модели с Hugging Face Hub (если они ещё не загружены). Используем модель Qwen1.5-0.5B-Chat в качестве примера:

```
# Запускаем VLLM-сервис и загружаем модель Qwen1.5-0.5B-Chat
python -m vllm.entrypoints.openai.api_server \
    --model Qwen/Qwen1.5-0.5B-Chat \
    --host 0.0.0.0 \
    --port 8000
```

После запуска сервиса он предоставит OpenAI-совместимый API по адресу `http://localhost:8000/v1`.

**Ollama**

Ollama упрощает управление и развёртывание локальных моделей ещё сильнее, оборачивая скачивание, настройку и запуск сервиса в единую команду, что делает его идеальным для быстрого старта. Посетите [официальный сайт](https://ollama.com) Ollama, чтобы скачать и установить клиент для вашей операционной системы.

После установки откройте терминал и выполните следующую команду для скачивания и запуска модели (используем Llama 3 в качестве примера). Ollama автоматически обработает скачивание модели, оборачивание в сервис и настройку аппаратного ускорения.

```
# При первом запуске модель скачивается автоматически; при последующих — сервис стартует сразу
ollama run llama3
```

Когда в терминале появится интерактивный промпт модели, это означает, что сервис успешно запущен в фоновом режиме. По умолчанию Ollama открывает OpenAI-совместимый API-интерфейс по адресу `http://localhost:11434/v1`.

**Интеграция с `HelloAgentsLLM`**

Поскольку и VLLM, и Ollama следуют стандарту API, интегрировать их в `HelloAgentsLLM` очень просто: достаточно указать их как новый `provider` при создании клиента.

Например, подключение к локально запущенному **VLLM**-сервису:

```python
llm_client = HelloAgentsLLM(
    provider="vllm",
    model="Qwen/Qwen1.5-0.5B-Chat",  # Должно совпадать с моделью, указанной при запуске сервиса

    api_key="vllm"  # Локальным сервисам обычно не нужен настоящий API Key — можно указать любую непустую строку
)
```

Или, задав переменные среды и позволив клиенту автоопределить провайдера, достичь нулевого изменения кода:

```bash
# Задаём в файле .env
LLM_BASE_URL="http://localhost:8000/v1"
LLM_API_KEY="vllm"

# В Python-коде просто создаём экземпляр
llm_client = HelloAgentsLLM()  # Автоматически определится как vllm
```

Аналогично, подключение к локальному **Ollama**-сервису:

```python
llm_client = HelloAgentsLLM(
    provider="ollama",
    model="llama3",  # Должно совпадать с моделью, указанной в `ollama run`
    base_url="http://localhost:11434/v1",
    api_key="ollama"  # Локальным сервисам тоже не нужен настоящий Key
)
```

Благодаря этому унифицированному дизайну ключевой код агента не требует изменений при переключении между облачными API и локальными моделями. Это даёт огромную гибкость при разработке последующих приложений, развёртывании, контроле затрат и защите приватности данных.

### 7.2.3 Механизм автоопределения

Чтобы максимально снизить нагрузку конфигурации на пользователя и следовать принципу «соглашение вместо настройки», внутри `HelloAgentsLLM` спроектированы два ключевых вспомогательных метода: `_auto_detect_provider` и `_resolve_credentials`. Они работают совместно: `_auto_detect_provider` отвечает за определение провайдера на основе информации из окружения, а `_resolve_credentials` завершает конкретную конфигурацию параметров на основе результата определения.

Метод `_auto_detect_provider` отвечает за автоматический вывод провайдера из информации окружения в следующем порядке приоритетов:

1. **Наивысший приоритет: проверка переменных среды конкретных провайдеров.** Это наиболее прямой и надёжный критерий. Фреймворк последовательно проверяет наличие переменных среды `MODELSCOPE_API_KEY`, `OPENAI_API_KEY`, `ZHIPU_API_KEY` и т. д. Как только найдена любая из них, сразу определяется соответствующий провайдер.

2. **Второй приоритет: определение по `base_url`.** Если пользователь не задал ключ конкретного провайдера, но задал универсальный `LLM_BASE_URL`, фреймворк анализирует этот URL.

   - **Совпадение домена**: Облачные провайдеры определяются по наличию в URL характерных строк: `"api-inference.modelscope.cn"`, `"api.openai.com"` и т. д.
   - **Совпадение порта**: Локальные решения определяются по стандартным портам: `:11434` (Ollama), `:8000` (VLLM) и т. д.

3. **Вспомогательное определение: анализ формата API-ключа.** В ряде случаев, когда первые два метода не дают результата, фреймворк пытается проанализировать формат универсальной переменной среды `LLM_API_KEY`. Например, у некоторых провайдеров ключи имеют фиксированные префиксы или уникальные форматы кодирования. Однако, поскольку этот метод может быть неоднозначным, его приоритет ниже — он используется лишь как вспомогательный.

Ключевой код метода:

```python
def _auto_detect_provider(self, api_key: Optional[str], base_url: Optional[str]) -> str:
    """
    Автоматически определяет провайдера LLM
    """
    # 1. Проверяем переменные среды конкретных провайдеров (наивысший приоритет)
    if os.getenv("MODELSCOPE_API_KEY"): return "modelscope"
    if os.getenv("OPENAI_API_KEY"): return "openai"
    if os.getenv("ZHIPU_API_KEY"): return "zhipu"
    # ... Проверки переменных среды других провайдеров

    # Получаем универсальные переменные среды
    actual_api_key = api_key or os.getenv("LLM_API_KEY")
    actual_base_url = base_url or os.getenv("LLM_BASE_URL")

    # 2. Определяем по base_url
    if actual_base_url:
        base_url_lower = actual_base_url.lower()
        if "api-inference.modelscope.cn" in base_url_lower: return "modelscope"
        if "open.bigmodel.cn" in base_url_lower: return "zhipu"
        if "localhost" in base_url_lower or "127.0.0.1" in base_url_lower:
            if ":11434" in base_url_lower: return "ollama"
            if ":8000" in base_url_lower: return "vllm"
            return "local"  # Другие локальные порты

    # 3. Вспомогательное определение по формату API-ключа
    if actual_api_key:
        if actual_api_key.startswith("ms-"): return "modelscope"
        # ... Прочие проверки форматов ключей

    # 4. По умолчанию возвращаем 'auto' — используем универсальную конфигурацию
    return "auto"
```

После определения `provider` (явно пользователем или автоматически) управление передаётся методу `_resolve_credentials`, который обрабатывает дифференцированную конфигурацию провайдеров. Он активно ищет соответствующие переменные среды на основе значения `provider` и задаёт `base_url` по умолчанию. Ключевые фрагменты реализации:

```python
def _resolve_credentials(self, api_key: Optional[str], base_url: Optional[str]) -> tuple[str, str]:
    """Определяет API-ключ и base_url на основе провайдера"""
    if self.provider == "openai":
        resolved_api_key = api_key or os.getenv("OPENAI_API_KEY") or os.getenv("LLM_API_KEY")
        resolved_base_url = base_url or os.getenv("LLM_BASE_URL") or "https://api.openai.com/v1"
        return resolved_api_key, resolved_base_url

    elif self.provider == "modelscope":
        resolved_api_key = api_key or os.getenv("MODELSCOPE_API_KEY") or os.getenv("LLM_API_KEY")
        resolved_base_url = base_url or os.getenv("LLM_BASE_URL") or "https://api-inference.modelscope.cn/v1/"
        return resolved_api_key, resolved_base_url

    # ... Логика для других провайдеров
```

Оценим удобство автоопределения на простом примере. Предположим, пользователь хочет использовать локальный Ollama-сервис — ему достаточно настроить файл `.env` следующим образом:

```bash

LLM_MODEL_ID="llama3"
```

Не нужно настраивать `LLM_API_KEY` и указывать `provider` в коде. Достаточно просто создать экземпляр `HelloAgentsLLM` в Python-коде:


## 7.3 Реализация интерфейсов фреймворка

В предыдущем разделе мы построили `HelloAgentsLLM` — ключевой компонент, решающий задачу коммуникации с большими языковыми моделями. Однако для управления потоками данных, конфигурацией, обработки исключений и создания чёткой унифицированной структуры для построения верхних слоёв приложений нужен ещё ряд вспомогательных интерфейсов. Этот раздел охватывает три основных файла:

- `message.py`: Определяет унифицированный формат сообщений внутри фреймворка, обеспечивая стандартизацию передачи информации между агентами и моделями.
- `config.py`: Предоставляет централизованное решение для управления конфигурацией, делая поведение фреймворка легко настраиваемым и расширяемым.
- `agent.py`: Определяет абстрактный базовый класс (`Agent`) для всех агентов, задавая единый интерфейс и спецификацию для реализации различных типов агентов в будущем.

### 7.3.1 Класс Message

В диалоге между агентами и большими языковыми моделями история разговора — это критически важный контекст. Для стандартизированного управления этой информацией мы спроектировали простой класс `Message`. В последующей главе о контекстной инженерии он будет расширен.

```python
"""Система сообщений"""
from typing import Optional, Dict, Any, Literal
from datetime import datetime
from pydantic import BaseModel

# Определяем тип роли сообщения, ограничивая допустимые значения
MessageRole = Literal["user", "assistant", "system", "tool"]

class Message(BaseModel):
    """Класс сообщения"""

    content: str
    role: MessageRole
    timestamp: datetime = None
    metadata: Optional[Dict[str, Any]] = None

    def __init__(self, content: str, role: MessageRole, **kwargs):
        super().__init__(
            content=content,
            role=role,
            timestamp=kwargs.get('timestamp', datetime.now()),
            metadata=kwargs.get('metadata', {})
        )

    def to_dict(self) -> Dict[str, Any]:
        """Конвертируем в формат словаря (формат OpenAI API)"""
        return {
            "role": self.role,
            "content": self.content
        }

    def __str__(self) -> str:
        return f"[{self.role}] {self.content}"
```

В дизайне этого класса несколько ключевых моментов. Во-первых, через `typing.Literal` мы строго ограничиваем значения поля `role` четырьмя типами: `"user"`, `"assistant"`, `"system"`, `"tool"` — это напрямую соответствует спецификации OpenAI API и обеспечивает типобезопасность. Помимо двух основных полей `content` и `role`, добавлены `timestamp` и `metadata` — резерв для логирования и расширения функциональности в будущем. Наконец, метод `to_dict()` — одна из ключевых функций: он конвертирует внутренний объект `Message` в словарный формат, совместимый с OpenAI API, воплощая принцип «богатый внутри, совместимый снаружи».

### 7.3.2 Класс Config

Ответственность класса `Config` — централизовать жёстко закодированные параметры конфигурации и поддерживать их чтение из переменных среды.

```python
"""Управление конфигурацией"""
import os
from typing import Optional, Dict, Any
from pydantic import BaseModel

class Config(BaseModel):
    """Класс конфигурации HelloAgents"""

    # Конфигурация LLM
    default_model: str = "gpt-3.5-turbo"
    default_provider: str = "openai"
    temperature: float = 0.7
    max_tokens: Optional[int] = None

    # Системная конфигурация
    debug: bool = False
    log_level: str = "INFO"

    # Прочая конфигурация
    max_history_length: int = 100

    @classmethod
    def from_env(cls) -> "Config":
        """Создаём конфигурацию из переменных среды"""
        return cls(
            debug=os.getenv("DEBUG", "false").lower() == "true",
            log_level=os.getenv("LOG_LEVEL", "INFO"),
            temperature=float(os.getenv("TEMPERATURE", "0.7")),
            max_tokens=int(os.getenv("MAX_TOKENS")) if os.getenv("MAX_TOKENS") else None,
        )

    def to_dict(self) -> Dict[str, Any]:
        """Конвертируем в словарь"""
        return self.dict()
```

Во-первых, мы логически делим элементы конфигурации на группы `Конфигурация LLM`, `Системная конфигурация` и т. д., что делает структуру понятной с первого взгляда. Во-вторых, каждый элемент имеет разумное значение по умолчанию, гарантируя работу фреймворка с нулевой конфигурацией. Ключевой элемент — метод класса `from_env()`: он позволяет переопределять конфигурацию по умолчанию через переменные среды без изменения кода, что особенно удобно при развёртывании в разных окружениях.

### 7.3.3 Абстрактный базовый класс Agent

Класс `Agent` — высокоуровневая абстракция всего фреймворка. Он определяет общее поведение и атрибуты, которыми должен обладать агент, не заботясь о конкретных методах реализации. Мы реализуем его через модуль Python `abc` (Abstract Base Classes), который вынуждает все конкретные реализации агентов (такие как `SimpleAgent`, `ReActAgent` и т. д. в последующих главах) следовать единому «интерфейсу».

```python
"""Базовый класс агента"""
from abc import ABC, abstractmethod
from typing import Optional, Any
from .message import Message
from .llm import HelloAgentsLLM
from .config import Config

class Agent(ABC):
    """Базовый класс агента"""

    def __init__(
        self,
        name: str,
        llm: HelloAgentsLLM,
        system_prompt: Optional[str] = None,
        config: Optional[Config] = None
    ):
        self.name = name
        self.llm = llm
        self.system_prompt = system_prompt
        self.config = config or Config()
        self._history: list[Message] = []

    @abstractmethod
    def run(self, input_text: str, **kwargs) -> str:
        """Запускаем агента"""
        pass

    def add_message(self, message: Message):
        """Добавляем сообщение в историю"""
        self._history.append(message)

    def clear_history(self):
        """Очищаем историю"""
        self._history.clear()

    def get_history(self) -> list[Message]:
        """Получаем историю"""
        return self._history.copy()

    def __str__(self) -> str:
        return f"Agent(name={self.name}, provider={self.llm.provider})"
```

Дизайн этого класса воплощает принцип абстракции в объектно-ориентированном программировании. Во-первых, он определяется как абстрактный класс, который нельзя инстанцировать напрямую, путём наследования от `ABC`. Его конструктор `__init__` чётко определяет ключевые зависимости агента: имя, экземпляр LLM, системный промпт и конфигурацию. Самое важное — метод `run`, декорированный `@abstractmethod`: он вынуждает все подклассы реализовать этот метод, гарантируя единую точку входа для всех агентов. Кроме того, базовый класс предоставляет общие методы управления историей, которые работают совместно с классом `Message`, отражая связь между компонентами.

На этом завершён дизайн и реализация базовых компонентов ядра фреймворка `HelloAgents`.

```python
# Добавляем в my_simple_agent.py
import re

class MySimpleAgent(SimpleAgent):
    # ... предыдущий метод __init__

    def run(self, input_text: str, max_tool_iterations: int = 3, **kwargs) -> str:
        """

        messages.append({"role": "system", "content": enhanced_system_prompt})

        # Добавляем сообщения из истории
        for msg in self._history:
            messages.append({"role": msg.role, "content": msg.content})

        # Добавляем текущее сообщение пользователя

        # Если вызов инструментов не включён — используем простую диалоговую логику

            self.add_message(Message(input_text, "user"))
            self.add_message(Message(response, "assistant"))

            return response

        # Логика с поддержкой нескольких раундов вызова инструментов
        return self._run_with_tools(messages, input_text, max_tool_iterations, **kwargs)

    def _get_enhanced_system_prompt(self) -> str:

        if not self.enable_tool_calling or not self.tool_registry:

        tools_section += "Вы можете использовать следующие инструменты для ответа на вопросы:\n"

        tools_section += "\n## Формат вызова инструментов\n"

        tools_section += "Результаты вызова инструментов будут автоматически вставлены в разговор, после чего вы сможете продолжить ответ на основе результатов.\n"
```

Реализуем ключевую логику вызова инструментов:

```python
# Добавляем в my_simple_agent.py
class MySimpleAgent(SimpleAgent):
    # ... предыдущие методы

    def _run_with_tools(self, messages: list, input_text: str, max_tool_iterations: int, **kwargs) -> str:
        """Логика запуска с поддержкой вызова инструментов"""
        current_iteration = 0
        final_response = ""

        while current_iteration < max_tool_iterations:
            # Вызываем LLM
            response = self.llm.invoke(messages, **kwargs)

            # Проверяем наличие вызовов инструментов
            tool_calls = self._parse_tool_calls(response)

            if tool_calls:
                print(f"🔧 Обнаружено вызовов инструментов: {len(tool_calls)}")
                # Выполняем все вызовы и собираем результаты
                tool_results = []
                clean_response = response

                for call in tool_calls:
                    result = self._execute_tool_call(call['tool_name'], call['parameters'])
                    tool_results.append(result)
                    # Удаляем маркеры вызова из ответа
                    clean_response = clean_response.replace(call['original'], "")

                # Формируем сообщение с результатами инструментов
                messages.append({"role": "assistant", "content": clean_response})

                # Добавляем результаты инструментов
                tool_results_text = "\n\n".join(tool_results)
                messages.append({"role": "user", "content": f"Результаты выполнения инструментов:\n{tool_results_text}\n\nПожалуйста, дайте полный ответ на основе этих результатов."})

                current_iteration += 1
                continue

            # Вызовов инструментов нет — это финальный ответ
            final_response = response
            break

        # Если достигнут лимит итераций, берём последний ответ
        if current_iteration >= max_tool_iterations and not final_response:
            final_response = self.llm.invoke(messages, **kwargs)

        # Сохраняем в историю
        self.add_message(Message(input_text, "user"))
        self.add_message(Message(final_response, "assistant"))
        print(f"✅ {self.name} ответ готов")

        return final_response

    def _parse_tool_calls(self, text: str) -> list:
        """Разбираем вызовы инструментов в тексте"""
        pattern = r'\[TOOL_CALL:([^:]+):([^\]]+)\]'
        matches = re.findall(pattern, text)

        tool_calls = []
        for tool_name, parameters in matches:
            tool_calls.append({
                'tool_name': tool_name.strip(),
                'parameters': parameters.strip(),
                'original': f'[TOOL_CALL:{tool_name}:{parameters}]'
            })

        return tool_calls

    def _execute_tool_call(self, tool_name: str, parameters: str) -> str:
        """Выполняем вызов инструмента"""
        if not self.tool_registry:
            return f"❌ Ошибка: реестр инструментов не настроен"

        try:
            # Интеллектуальный разбор параметров
            if tool_name == 'calculator':
                # Калькулятор принимает выражение напрямую
                result = self.tool_registry.execute_tool(tool_name, parameters)
            else:
                # Остальные инструменты используют интеллектуальный разбор параметров
                param_dict = self._parse_tool_parameters(tool_name, parameters)
                tool = self.tool_registry.get_tool(tool_name)
                if not tool:
                    return f"❌ Ошибка: инструмент '{tool_name}' не найден"
                result = tool.run(param_dict)

            return f"🔧 Результат выполнения инструмента {tool_name}:\n{result}"

        except Exception as e:
            return f"❌ Вызов инструмента завершился ошибкой: {str(e)}"

    def _parse_tool_parameters(self, tool_name: str, parameters: str) -> dict:
        """Интеллектуальный разбор параметров инструмента"""
        param_dict = {}

        if '=' in parameters:
            # Формат: key=value или action=search,query=Python
            if ',' in parameters:
                # Несколько параметров: action=search,query=Python,limit=3
                pairs = parameters.split(',')
                for pair in pairs:
                    if '=' in pair:
                        key, value = pair.split('=', 1)
                        param_dict[key.strip()] = value.strip()
            else:
                # Один параметр: key=value
                key, value = parameters.split('=', 1)
                param_dict[key.strip()] = value.strip()
        else:
            # Передаём параметры напрямую, интеллектуально определяя тип по имени инструмента
            if tool_name == 'search':
                param_dict = {'query': parameters}
            elif tool_name == 'memory':
                param_dict = {'action': 'search', 'query': parameters}
            else:
                param_dict = {'input': parameters}

        return param_dict
```

```python
class MySimpleAgent(SimpleAgent):
    # ... предыдущие методы

    def stream_run(self, input_text: str, **kwargs) -> Iterator[str]:
        """
        Кастомный метод запуска со стримингом
        """
        print(f"🌊 {self.name} начинает потоковую обработку: {input_text}")

        messages = []

        if self.system_prompt:
            messages.append({"role": "system", "content": self.system_prompt})

        for msg in self._history:
            messages.append({"role": msg.role, "content": msg.content})

        messages.append({"role": "user", "content": input_text})

        # Стриминговый вызов LLM
        full_response = ""
        print("📝 Ответ в реальном времени: ", end="")
        for chunk in self.llm.stream_invoke(messages, **kwargs):
            full_response += chunk
            print(chunk, end="", flush=True)
            yield chunk

        print()  # Переносим строку

        # Сохраняем полный диалог в историю
        self.add_message(Message(input_text, "user"))
        self.add_message(Message(full_response, "assistant"))
        print(f"✅ {self.name} потоковый ответ завершён")

    def add_tool(self, tool) -> None:
        """Добавляем инструмент в агент (удобный метод)"""
        if not self.tool_registry:
            from hello_agents import ToolRegistry
            self.tool_registry = ToolRegistry()
            self.enable_tool_calling = True

        self.tool_registry.register_tool(tool)
        print(f"🔧 Инструмент '{tool.name}' добавлен")

    def has_tools(self) -> bool:
        """Проверяем наличие доступных инструментов"""
        return self.enable_tool_calling and self.tool_registry is not None

    def remove_tool(self, tool_name: str) -> bool:
        """Удаляем инструмент (удобный метод)"""
        if self.tool_registry:
            self.tool_registry.unregister(tool_name)
            return True
        return False

    def list_tools(self) -> list:
        """Получаем список всех доступных инструментов"""
        if self.tool_registry:
            return self.tool_registry.list_tools()
        return []
```

### 7.4.2 ReActAgent

ReActAgent в версии для фреймворка сохраняет ключевую логику неизменной, но улучшает организацию кода и сопровождаемость — главным образом за счёт оптимизации промптов и интеграции с системой инструментов фреймворка.

**(1) Улучшение шаблона промпта**

ReActAgent в версии для фреймворка декомпозирует процесс выполнения на чёткие шаги:

```python
def run(self, input_text: str, **kwargs) -> str:
    """Запускаем ReAct-агент"""
    self.current_history = []
    current_step = 0

    print(f"\n🤖 {self.name} начинает обработку вопроса: {input_text}")

    while current_step < self.max_steps:
        current_step += 1
        print(f"\n--- Шаг {current_step} ---")

        # 1. Строим промпт
        tools_desc = self.tool_registry.get_tools_description()
        history_str = "\n".join(self.current_history)
        prompt = self.prompt_template.format(
            tools=tools_desc,
            question=input_text,
            history=history_str
        )

        # 2. Вызываем LLM
        messages = [{"role": "user", "content": prompt}]
        response_text = self.llm.invoke(messages, **kwargs)

        # 3. Разбираем вывод
        thought, action = self._parse_output(response_text)

        # 4. Проверяем условие завершения
        if action and action.startswith("Finish"):
            final_answer = self._parse_action_input(action)
            self.add_message(Message(input_text, "user"))
            self.add_message(Message(final_answer, "assistant"))
            return final_answer

        # 5. Выполняем вызов инструмента
        if action:
            tool_name, tool_input = self._parse_action(action)
            observation = self.tool_registry.execute_tool(tool_name, tool_input)
            self.current_history.append(f"Действие: {action}")
            self.current_history.append(f"Наблюдение: {observation}")

    # Достигнут максимум шагов
    final_answer = "Извините, не удалось выполнить задачу в рамках ограниченного числа шагов."
    self.add_message(Message(input_text, "user"))
    self.add_message(Message(final_answer, "assistant"))
    return final_answer
```

### 7.4.5 FunctionCallAgent

FunctionCallAgent — агент, введённый в hello-agents начиная с версии 0.2.8 на основе нативного механизма вызова функций OpenAI. Он демонстрирует, как строить агент с использованием возможностей Function Calling OpenAI.
Поддерживает следующие функции:

- `_build_tool_schemas`: Строит схему вызова функций OpenAI через описания инструментов
- `_extract_message_content`: Извлекает текстовое содержимое из ответов OpenAI
- `_parse_function_call_arguments`: Разбирает параметры JSON, возвращаемые моделью
- `_convert_parameter_types`: Конвертирует типы параметров

Эти возможности обеспечивают нативный Function Calling OpenAI, который надёжнее подходов на основе ограничений через промпты.

```python
def _invoke_with_tools(self, messages: list[dict[str, Any]], tools: list[dict[str, Any]], tool_choice: Union[str, dict], **kwargs):
        """Вызываем базовый клиент OpenAI для выполнения вызовов функций"""

        client = getattr(self.llm, "_client", None)
        if client is None:
            raise RuntimeError("Клиент HelloAgentsLLM не инициализирован должным образом — выполнение вызовов функций невозможно.")

        client_kwargs.setdefault("temperature", self.llm.temperature)
        if self.llm.max_tokens is not None:
            client_kwargs.setdefault("max_tokens", self.llm.max_tokens)

        return client.chat.completions.create(
            model=self.llm.model,
            messages=messages,
            tools=tools,
            tool_choice=tool_choice,
            **client_kwargs,
        )
```

## 7.5 Система инструментов

Содержание этого раздела — глубокое изучение дизайна и реализации системы инструментов на основе созданной ранее инфраструктуры агентов. Мы начнём с построения базовой инфраструктуры и постепенно углубимся в кастомную разработку. Цели обучения этого раздела строятся вокруг трёх ключевых аспектов:

2. **Практикоориентированная разработка инструментов**: На примере инструмента математических вычислений продемонстрировать, как проектировать и реализовывать кастомные инструменты, освоив полный процесс разработки.

3. **Продвинутые стратегии интеграции и оптимизации**: Через дизайн инструмента многоисточникового поиска показать, как интегрировать несколько внешних сервисов, реализовать интеллектуальный выбор бэкенда, объединение результатов и отказоустойчивость, отражая проектное мышление системы инструментов в сложных сценариях.

### 7.5.1 Дизайн базового класса инструментов и механизма регистрации

При построении расширяемой системы инструментов нужно сначала создать стандартизированную инфраструктуру. Она включает базовый класс Tool, реестр ToolRegistry и механизмы управления инструментами.

**(1) Абстрактный дизайн базового класса Tool**

Базовый класс Tool — ключевая абстракция всей системы инструментов, определяющая спецификации интерфейса, которым должны следовать все инструменты:

````python
class Tool(ABC):
    """Базовый класс инструмента"""

    def __init__(self, name: str, description: str):
        self.name = name
        self.description = description

    @abstractmethod
    def run(self, parameters: Dict[str, Any]) -> str:
        """Выполняем инструмент"""
        pass

    @abstractmethod
    def get_parameters(self) -> List[ToolParameter]:
        """Получаем определения параметров инструмента"""
        pass
````

Этот дизайн воплощает ключевую идею объектно-ориентированного проектирования: через унифицированный интерфейс метода `run` все инструменты могут выполняться единообразно — принимают словарь параметров и возвращают строковый результат, обеспечивая согласованность фреймворка. Одновременно инструменты обладают возможностью самоописания: через метод `get_parameters` они явно сообщают вызывающей стороне, какие параметры им нужны. Этот механизм интроспекции создаёт основу для автоматической генерации документации и валидации параметров. Метаданные — имя и описание — придают системе инструментов хорошую обнаруживаемость и понятность.

**(2) Система определения параметров ToolParameter**

Для поддержки сложной валидации параметров и генерации документации мы спроектировали класс ToolParameter:

````python
class ToolParameter(BaseModel):
    """Определение параметра инструмента"""
    name: str
    type: str
    description: str
    required: bool = True
    default: Any = None
````

Этот дизайн позволяет инструментам точно описывать требования к параметрам, поддерживая проверку типов, задание значений по умолчанию и автоматическую генерацию документации.

**(3) Реализация ToolRegistry**

ToolRegistry — управляющий хаб системы инструментов, предоставляющий ключевые функции регистрации, обнаружения и выполнения инструментов. В этом разделе мы главным образом используем следующие функции:

````python
class ToolRegistry:
    """Реестр инструментов HelloAgents"""

    def __init__(self):
        self._tools: dict[str, Tool] = {}
        self._functions: dict[str, dict[str, Any]] = {}

    def register_tool(self, tool: Tool):
        """Регистрируем объект Tool"""
        if tool.name in self._tools:
            print(f"⚠️ Предупреждение: инструмент '{tool.name}' уже существует и будет перезаписан.")
        self._tools[tool.name] = tool
        print(f"✅ Инструмент '{tool.name}' зарегистрирован.")

    def register_function(self, name: str, description: str, func: Callable[[str], str]):
        """
        Напрямую регистрируем функцию как инструмент (удобный метод)

        Args:
            name: Имя инструмента
            description: Описание инструмента
            func: Функция инструмента — принимает строку, возвращает строку
        """
        if name in self._functions:
            print(f"⚠️ Предупреждение: инструмент '{name}' уже существует и будет перезаписан.")

        self._functions[name] = {
            "description": description,
            "func": func
        }
        print(f"✅ Инструмент '{name}' зарегистрирован.")
````

ToolRegistry поддерживает два способа регистрации:

1. **Регистрация объекта Tool**: Подходит для сложных инструментов, поддерживает полное определение и валидацию параметров
2. **Прямая регистрация функции**: Подходит для простых инструментов, быстро интегрирует существующие функции

**(4) Механизм обнаружения и управления инструментами**

Реестр предоставляет богатые функции управления инструментами:

````python
def get_tools_description(self) -> str:
    """Получаем отформатированную строку описания всех доступных инструментов"""
    descriptions = []

    # Описания объектов-инструментов
    for tool in self._tools.values():
        descriptions.append(f"- {tool.name}: {tool.description}")

    # Описания инструментов-функций
    for name, info in self._functions.items():
        descriptions.append(f"- {name}: {info['description']}")

    return "\n".join(descriptions) if descriptions else "Инструменты недоступны"
````

Строка описания, генерируемая этим методом, может напрямую использоваться для построения промпта агента, сообщая ему, какие инструменты доступны.

### 7.5.2 Разработка кастомного инструмента

Имея инфраструктуру, посмотрим, как разработать полноценный кастомный инструмент. Инструмент математических вычислений — хороший пример: простой и наглядный. Наиболее прямой способ — воспользоваться функцией регистрации функций ToolRegistry.

Создадим кастомный инструмент математических вычислений. Сначала создайте `my_calculator_tool.py` в директории проекта:

```python
# my_calculator_tool.py
import ast
import operator
import math
from hello_agents import ToolRegistry

def my_calculate(expression: str) -> str:
    """Простая функция математических вычислений"""
    if not expression.strip():
        return "Выражение для вычисления не может быть пустым"

    # Поддерживаемые базовые операции
    operators = {
        ast.Add: operator.add,      # +
        ast.Sub: operator.sub,      # -
        ast.Mult: operator.mul,     # *
        ast.Div: operator.truediv,  # /
    }

    # Поддерживаемые базовые функции
    functions = {
        'sqrt': math.sqrt,
        'pi': math.pi,
    }

    try:
        node = ast.parse(expression, mode='eval')
        result = _eval_node(node.body, operators, functions)
        return str(result)
    except:
        return "Вычисление не удалось — проверьте формат выражения"

def _eval_node(node, operators, functions):
    """Упрощённое вычисление выражений"""
    if isinstance(node, ast.Constant):
        return node.value
    elif isinstance(node, ast.BinOp):
        left = _eval_node(node.left, operators, functions)
        right = _eval_node(node.right, operators, functions)
        op = operators.get(type(node.op))
        return op(left, right)
    elif isinstance(node, ast.Call):
        func_name = node.func.id
        if func_name in functions:
            args = [_eval_node(arg, operators, functions) for arg in node.args]
            return functions[func_name](*args)
    elif isinstance(node, ast.Name):
        if node.id in functions:
            return functions[node.id]

def create_calculator_registry():
    """Создаём реестр инструментов с калькулятором"""
    registry = ToolRegistry()

    # Регистрируем функцию калькулятора
    registry.register_function(
        name="my_calculator",
        description="Простой инструмент математических вычислений, поддерживает базовые операции (+,-,*,/) и функцию sqrt",
        func=my_calculate
    )

    return registry
```

Инструмент поддерживает не только базовые арифметические операции, но и часто используемые математические функции и константы. Вы также можете самостоятельно расширить этот файл для создания более полной функции вычислений. Предоставляем тестовый файл `test_my_calculator.py` для проверки функциональности:

### 7.5.3 Инструмент многоисточникового поиска

В практических приложениях часто нужно интегрировать несколько внешних сервисов для более мощного функционала. Поисковые инструменты — типичный пример: интеграция нескольких поисковых систем даёт более полную актуальную информацию. В главе 1 мы использовали Tavily API, в главе 4 — SerpApi. Поэтому на этот раз используем оба API для реализации многоисточникового поиска. Если соответствующие Python-зависимости ещё не установлены, выполните:

**(1) Дизайн унифицированного интерфейса для поисковых инструментов**

Встроенный в HelloAgents `SearchTool` демонстрирует, как спроектировать продвинутый многоисточниковый инструмент поиска:

````python
class SearchTool(Tool):
    """
    Интеллектуальный гибридный поисковый инструмент

    Поддерживает несколько поисковых бэкендов, интеллектуально выбирает лучший источник:
    1. Гибридный режим (hybrid) — интеллектуально выбирает TAVILY или SERPAPI
    2. Tavily API (tavily) — профессиональный AI-поиск
    3. SerpApi (serpapi) — традиционный поиск Google
    """

    def __init__(self, backend: str = "hybrid", tavily_key: Optional[str] = None, serpapi_key: Optional[str] = None):
        super().__init__(
            name="search",
            description="Интеллектуальная поисковая система. Поддерживает гибридный режим, автоматически выбирает лучший источник."
        )
        self.backend = backend
        self.tavily_key = tavily_key or os.getenv("TAVILY_API_KEY")
        self.serpapi_key = serpapi_key or os.getenv("SERPAPI_API_KEY")
        self.available_backends = []
        self._setup_backends()
````

Ключевая идея этого дизайна — автоматически выбирать лучший поисковый бэкенд на основе доступных API-ключей и библиотек.

**(2) Стратегия интеграции поисковых источников TAVILY и SERPAPI**

Фреймворк реализует логику интеллектуального выбора бэкенда:

````python
def _search_hybrid(self, query: str) -> str:
    """Гибридный поиск — интеллектуально выбирает лучший источник"""
    # Приоритет: Tavily (AI-оптимизированный поиск)
    if "tavily" in self.available_backends:
        try:
            return self._search_tavily(query)
        except Exception as e:
            print(f"⚠️ Поиск Tavily не удался: {e}")
            # При сбое Tavily пробуем SerpApi
            if "serpapi" in self.available_backends:
                print("🔄 Переключаемся на поиск SerpApi")
                return self._search_serpapi(query)

    # Если Tavily недоступен — используем SerpApi
    elif "serpapi" in self.available_backends:
        try:
            return self._search_serpapi(query)
        except Exception as e:
            print(f"⚠️ Поиск SerpApi не удался: {e}")

    # Если оба недоступны — предлагаем пользователю настроить API
    return "❌ Нет доступных источников поиска — задайте переменные среды TAVILY_API_KEY или SERPAPI_API_KEY"
````

Этот дизайн воплощает ключевую концепцию высокодоступных систем: через механизм деградации система поэтапно переходит от оптимального к доступным альтернативным источникам. Когда все источники недоступны, чётко подсказывает пользователю настроить правильные API-ключи.

**(3) Унификация форматирования результатов поиска**

Разные поисковые системы возвращают результаты в разных форматах. Фреймворк обрабатывает это через унифицированный метод форматирования:

````python
def _search_tavily(self, query: str) -> str:
    """Поиск через Tavily"""

        query=query,
        search_depth="basic",
        include_answer=True,
        max_results=3

    result = f"🎯 Результаты AI-поиска Tavily: {response.get('answer', 'Прямой ответ не найден')}\n\n"

    for i, item in enumerate(response.get('results', [])[:3], 1):
        result += f"[{i}] {item.get('title', '')}\n"
        result += f"    {item.get('content', '')[:200]}...\n"
        result += f"    Источник: {item.get('url', '')}\n\n"

    return result
````

Основываясь на философии проектирования фреймворка, создадим собственный продвинутый инструмент поиска. На этот раз используем подход на основе класса для демонстрации разных методов реализации. Создайте `my_advanced_search.py`:

```python
# my_advanced_search.py
import os
from typing import Optional, List, Dict, Any
from hello_agents import ToolRegistry

class MyAdvancedSearchTool:
    """
    Кастомный продвинутый инструмент поиска.
    Демонстрирует паттерны проектирования для многоисточниковой интеграции и интеллектуального выбора.
    """

    def __init__(self):
        self.name = "my_advanced_search"
        self.description = "Интеллектуальный поисковый инструмент, поддерживает несколько источников, автоматически выбирает лучший результат"
        self.search_sources = []
        self._setup_search_sources()

    def _setup_search_sources(self):
        """Настраиваем доступные источники поиска"""
        # Проверяем доступность Tavily
        if os.getenv("TAVILY_API_KEY"):
            try:
                from tavily import TavilyClient
                self.tavily_client = TavilyClient(api_key=os.getenv("TAVILY_API_KEY"))
                self.search_sources.append("tavily")
                print("✅ Источник поиска Tavily активирован")
            except ImportError:
                print("⚠️ Библиотека Tavily не установлена")

        # Проверяем доступность SerpApi
        if os.getenv("SERPAPI_API_KEY"):
            try:
                import serpapi
                self.search_sources.append("serpapi")
                print("✅ Источник поиска SerpApi активирован")
            except ImportError:
                print("⚠️ Библиотека SerpApi не установлена")

        if self.search_sources:
            print(f"🔧 Доступные источники поиска: {', '.join(self.search_sources)}")
        else:
            print("⚠️ Нет доступных источников поиска — задайте API-ключи")

    def search(self, query: str) -> str:
        """Выполняем интеллектуальный поиск"""
        if not query.strip():
            return "❌ Ошибка: поисковый запрос не может быть пустым"

        # Проверяем наличие доступных источников
        if not self.search_sources:
            return """❌ Нет доступных источников поиска. Задайте один из следующих API-ключей:

1. Tavily API: задайте переменную среды TAVILY_API_KEY
   Получить: https://tavily.com/

2. SerpAPI: задайте переменную среды SERPAPI_API_KEY
   Получить: https://serpapi.com/

После настройки перезапустите программу."""

        print(f"🔍 Запускаем интеллектуальный поиск: {query}")

        # Пробуем несколько источников, возвращаем лучший результат
        for source in self.search_sources:
            try:
                if source == "tavily":
                    result = self._search_with_tavily(query)
                    if result and "not found" not in result.lower():
                        return f"📊 Результаты AI-поиска Tavily:\n\n{result}"

                elif source == "serpapi":
                    result = self._search_with_serpapi(query)
                    if result and "not found" not in result.lower():
                        return f"🌐 Результаты Google-поиска SerpApi:\n\n{result}"

            except Exception as e:
                print(f"⚠️ Поиск {source} не удался: {e}")
                continue

        return "❌ Все источники поиска недоступны — проверьте подключение к сети и конфигурацию API-ключей"

    def _search_with_tavily(self, query: str) -> str:
        """Поиск через Tavily"""
        response = self.tavily_client.search(query=query, max_results=3)

        if response.get('answer'):
            result = f"💡 Прямой AI-ответ: {response['answer']}\n\n"
        else:
            result = ""

        result += "🔗 Связанные результаты:\n"
        for i, item in enumerate(response.get('results', [])[:3], 1):
            result += f"[{i}] {item.get('title', '')}\n"
            result += f"    {item.get('content', '')[:150]}...\n\n"

        return result

    def _search_with_serpapi(self, query: str) -> str:
        """Поиск через SerpApi"""
        import serpapi

        search = serpapi.GoogleSearch({
            "q": query,
            "api_key": os.getenv("SERPAPI_API_KEY"),
            "num": 3
        })

        results = search.get_dict()

        result = "🔗 Результаты поиска Google:\n"
        if "organic_results" in results:
            for i, res in enumerate(results["organic_results"][:3], 1):
                result += f"[{i}] {res.get('title', '')}\n"
                result += f"    {res.get('snippet', '')}\n\n"

        return result

def create_advanced_search_registry():
    """Создаём реестр с продвинутым инструментом поиска"""
    registry = ToolRegistry()

    # Создаём экземпляр поискового инструмента
    search_tool = MyAdvancedSearchTool()

    # Регистрируем метод поиска как функцию
    registry.register_function(
        name="advanced_search",
        description="Продвинутый поисковый инструмент, интегрирует несколько источников Tavily и SerpAPI, обеспечивая более полные результаты",
        func=search_tool.search
    )

    return registry
```

### 7.5.4 Продвинутые возможности системы инструментов

Освоив базовую разработку инструментов и многоисточниковую интеграцию, изучим продвинутые возможности системы инструментов. Они позволяют системе стабильно работать в сложных производственных средах и предоставлять агентам более мощный функционал.

**(1) Механизм цепочки инструментов**

На практике агентам часто нужно комбинировать несколько инструментов для выполнения сложных задач. Спроектируем менеджер цепочек инструментов, заимствуя концепцию графа из главы 6:

```python
# tool_chain_manager.py
from typing import List, Dict, Any, Optional
from hello_agents import ToolRegistry

class ToolChain:
    """Цепочка инструментов — поддерживает последовательное выполнение нескольких инструментов"""

    def __init__(self, name: str, description: str):
        self.name = name
        self.description = description
        self.steps: List[Dict[str, Any]] = []

    def add_step(self, tool_name: str, input_template: str, output_key: str = None):
        """
        Добавляем шаг выполнения инструмента

        Args:
            tool_name: Имя инструмента
            input_template: Шаблон входных данных, поддерживает подстановку переменных
            output_key: Ключ для результата, используемый для ссылки в последующих шагах
        """
        self.steps.append({
            "tool_name": tool_name,
            "input_template": input_template,
            "output_key": output_key or f"step_{len(self.steps)}_result"
        })

    def execute(self, registry: ToolRegistry, initial_input: str, context: Dict[str, Any] = None) -> str:
        """Выполняем цепочку инструментов"""
        context = context or {}
        context["input"] = initial_input

        print(f"🔗 Запускаем выполнение цепочки инструментов: {self.name}")

        for i, step in enumerate(self.steps, 1):
            tool_name = step["tool_name"]
            input_template = step["input_template"]
            output_key = step["output_key"]

            # Подставляем переменные в шаблон
            try:
                tool_input = input_template.format(**context)
            except KeyError as e:
                return f"❌ Выполнение цепочки не удалось: переменная шаблона {e} не найдена"

            print(f"  Шаг {i}: используем {tool_name} для обработки '{tool_input[:50]}...'")

            # Выполняем инструмент
            result = registry.execute_tool(tool_name, tool_input)
            context[output_key] = result

            print(f"  ✅ Шаг {i} завершён, длина результата: {len(result)} символов")

        # Возвращаем результат последнего шага
        final_result = context[self.steps[-1]["output_key"]]
        print(f"🎉 Цепочка инструментов '{self.name}' выполнена")
        return final_result

class ToolChainManager:
    """Менеджер цепочек инструментов"""

    def __init__(self, registry: ToolRegistry):
        self.registry = registry
        self.chains: Dict[str, ToolChain] = {}

    def register_chain(self, chain: ToolChain):
        """Регистрируем цепочку инструментов"""
        self.chains[chain.name] = chain
        print(f"✅ Цепочка инструментов '{chain.name}' зарегистрирована")

    def execute_chain(self, chain_name: str, input_data: str, context: Dict[str, Any] = None) -> str:
        """Выполняем указанную цепочку инструментов"""
        if chain_name not in self.chains:
            return f"❌ Цепочка инструментов '{chain_name}' не существует"

        chain = self.chains[chain_name]
        return chain.execute(self.registry, input_data, context)

    def list_chains(self) -> List[str]:
        """Получаем список всех цепочек инструментов"""
        return list(self.chains.keys())

# Пример использования
def create_research_chain() -> ToolChain:
    """Создаём исследовательскую цепочку: поиск -> вычисление -> резюме"""
    chain = ToolChain(
        name="research_and_calculate",
        description="Поиск информации и выполнение связанных вычислений"
    )

    # Шаг 1: поиск информации
    chain.add_step(
        tool_name="search",
        input_template="{input}",
        output_key="search_result"
    )

    # Шаг 2: выполнение вычислений на основе результатов поиска (при необходимости)
    chain.add_step(
        tool_name="my_calculator",
        input_template="Вычисли соответствующие значения на основе следующей информации: {search_result}",
        output_key="calculation_result"
    )

    return chain
```

**(2) Поддержка асинхронного выполнения инструментов**

Для длительных операций с инструментами предоставим поддержку асинхронного выполнения:

```python
# async_tool_executor.py
import asyncio
import concurrent.futures
from typing import Dict, Any, List, Callable
from hello_agents import ToolRegistry

class AsyncToolExecutor:
    """Асинхронный исполнитель инструментов"""

    def __init__(self, registry: ToolRegistry, max_workers: int = 4):
        self.registry = registry
        self.executor = concurrent.futures.ThreadPoolExecutor(max_workers=max_workers)

    async def execute_tool_async(self, tool_name: str, input_data: str) -> str:
        """Асинхронно выполняем один инструмент"""
        loop = asyncio.get_event_loop()

        def _execute():
            return self.registry.execute_tool(tool_name, input_data)

        result = await loop.run_in_executor(self.executor, _execute)
        return result

    async def execute_tools_parallel(self, tasks: List[Dict[str, str]]) -> List[str]:
        """Параллельно выполняем несколько инструментов"""
        print(f"🚀 Запускаем параллельное выполнение {len(tasks)} задач инструментов")

        # Создаём асинхронные задачи
        async_tasks = []
        for task in tasks:
            tool_name = task["tool_name"]
            input_data = task["input_data"]
            async_task = self.execute_tool_async(tool_name, input_data)
            async_tasks.append(async_task)

        # Ожидаем завершения всех задач
        results = await asyncio.gather(*async_tasks)

        print(f"✅ Все задачи инструментов завершены")
        return results

    def __del__(self):
        """Освобождаем ресурсы"""
        if hasattr(self, 'executor'):
            self.executor.shutdown(wait=True)

# Пример использования
async def test_parallel_execution():
    """Тестируем параллельное выполнение инструментов"""
    from hello_agents import ToolRegistry

    registry = ToolRegistry()
    # Предполагаем, что инструменты search и calculator уже зарегистрированы

    executor = AsyncToolExecutor(registry)

    # Определяем параллельные задачи
    tasks = [
        {"tool_name": "search", "input_data": "Python программирование"},
        {"tool_name": "search", "input_data": "машинное обучение"},
        {"tool_name": "my_calculator", "input_data": "2 + 2"},
        {"tool_name": "my_calculator", "input_data": "sqrt(16)"},
    ]

    # Выполняем параллельно
    results = await executor.execute_tools_parallel(tasks)

    for i, result in enumerate(results):
        print(f"Результат задачи {i+1}: {result[:100]}...")
```

На основе приведённого опыта проектирования и реализации можно сформулировать ключевые концепции разработки системы инструментов: на уровне проектирования каждый инструмент должен следовать принципу единой ответственности, сосредотачиваясь на конкретном функционале при сохранении единообразия интерфейса; комплексная обработка исключений и валидация входных данных с приоритетом безопасности — базовые требования. В плане оптимизации производительности используйте асинхронное выполнение для улучшения возможностей параллельной обработки, разумно управляя внешними соединениями и системными ресурсами.
