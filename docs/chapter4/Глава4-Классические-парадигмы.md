# Глава 4: Построение классических парадигм агентов

В предыдущей главе мы глубоко изучили большие языковые модели как «мозг» современных агентов: разобрали внутреннюю архитектуру Transformer, способы взаимодействия с ними и границы их возможностей. Теперь пора превратить эти теоретические знания в практику и построить агентов своими руками.

Ключевая способность современного агента — соединять мощь рассуждений LLM с внешним миром. Агент умеет самостоятельно понимать намерение пользователя, декомпозировать сложные задачи и достигать целей, вызывая ряд «инструментов» — интерпретаторов кода, поисковых систем, API — для получения информации и выполнения операций. Вместе с тем агенты не всесильны: они сталкиваются с проблемой «галлюцинаций», свойственных большим моделям, с риском зацикливания при сложных задачах и с некорректным использованием инструментов — всё это составляет границы возможностей агентов.

Для организации процессов «мышления» и «действия» агентов в индустрии сложилось несколько классических архитектурных парадигм. В этой главе мы сосредоточимся на трёх наиболее представительных и реализуем их с нуля шаг за шагом:

- **ReAct (Reasoning and Acting):** Парадигма, тесно объединяющая «мышление» и «действие», — агент думает и действует одновременно, динамически корректируя курс.
- **Plan-and-Solve:** Парадигма «сначала подумай, потом действуй» — агент сначала составляет полный план действий, а затем строго его исполняет.
- **Reflection:** Парадигма, наделяющая агента способностью к «рефлексии» — оптимизации результатов посредством самокритики и исправления ошибок.

После их изучения у вас может возникнуть вопрос: раз уже существуют отличные фреймворки вроде LangChain и LlamaIndex, зачем «изобретать велосипед»? Ответ прост. Во-первых, хотя зрелые фреймворки значительно ускоряют разработку, использование сильно абстрагированных инструментов не даёт понимания того, как работают базовые механизмы и какую пользу они приносят. Во-вторых, ручная реализация обнажает инженерные сложности: фреймворки берут на себя разбор форматов вывода модели, повторные попытки при сбоях вызова инструментов, предотвращение бесконечных циклов — столкнуться с этим лично и есть самый прямой путь к развитию навыков системного проектирования. Наконец, и это главное: владение принципами проектирования позволяет по-настоящему превратиться из «пользователя» фреймворка в «создателя» интеллектуальных приложений. Когда стандартные компоненты не справляются со сложными задачами, у вас будет возможность глубоко кастомизировать систему или выстроить совершенно новый агент с нуля.

### 4.1.3 Инкапсуляция базовых функций вызова LLM

Для большей чёткости и повторного использования кода определим специализированный класс-клиент LLM. Он инкапсулирует все детали взаимодействия с сервисом модели, позволяя основной логике сосредоточиться непосредственно на построении агента.

```python
import os
from openai import OpenAI
from dotenv import load_dotenv
from typing import List, Dict

# Загружаем переменные окружения из файла .env
load_dotenv()

class HelloAgentsLLM:
    """
    Кастомный LLM-клиент для книги «Hello Agents».
    Используется для вызова любого сервиса, совместимого с интерфейсом OpenAI;
    по умолчанию применяет потоковый вывод.
    """
    def __init__(self, model: str = None, apiKey: str = None, baseUrl: str = None, timeout: int = None):
        """
        Инициализирует клиент. Приоритет у переданных параметров;
        если они не указаны, значения берутся из переменных окружения.
        """
        self.model = model or os.getenv("LLM_MODEL_ID")
        apiKey = apiKey or os.getenv("LLM_API_KEY")
        baseUrl = baseUrl or os.getenv("LLM_BASE_URL")
        timeout = timeout or int(os.getenv("LLM_TIMEOUT", 60))
        
        if not all([self.model, apiKey, baseUrl]):
            raise ValueError("Необходимо указать ID модели, ключ API и адрес сервиса или определить их в файле .env.")

        self.client = OpenAI(api_key=apiKey, base_url=baseUrl, timeout=timeout)

    def think(self, messages: List[Dict[str, str]], temperature: float = 0) -> str:
        """
        Вызывает большую языковую модель для «размышления» и возвращает ответ.
        """
        print(f"🧠 Вызов модели {self.model}...")
        try:
            response = self.client.chat.completions.create(
                model=self.model,
                messages=messages,
                temperature=temperature,
                stream=True,
            )
            
            # Обработка потокового ответа
            print("✅ Большая языковая модель ответила успешно:")
            collected_content = []
            for chunk in response:
                if not chunk.choices:
                    continue
                content = chunk.choices[0].delta.content or ""
                print(content, end="", flush=True)
                collected_content.append(content)
            print()  # Перевод строки после завершения потокового вывода
            return "".join(collected_content)

        except Exception as e:
            print(f"❌ Ошибка при вызове LLM API: {e}")
            return None

# --- Пример использования клиента ---
if __name__ == '__main__':
    try:
        llmClient = HelloAgentsLLM()
        
        exampleMessages = [
            {"role": "system", "content": "You are a helpful assistant that writes Python code."},
            {"role": "user", "content": "Write a quicksort algorithm"}
        ]
        
        print("--- Вызов LLM ---")
        responseText = llmClient.think(exampleMessages)
        if responseText:
            print("\n\n--- Полный ответ модели ---")
            print(responseText)

    except ValueError as e:
        print(e)


>>>

Быстрая сортировка (Quicksort) — очень эффективный алгоритм сортировки...
```

## 4.2 ReAct

Подготовив LLM-клиент, мы построим первую и наиболее классическую парадигму агента: **ReAct (Reasoning + Acting)**. ReAct был предложен Шуньюем Яо в 2022 году<sup>[1]</sup>. Его ключевая идея — имитировать человеческий подход к решению задач, явно объединяя **Рассуждение (Reasoning)** и **Действие (Acting)** в цикл «думать–действовать–наблюдать».

### 4.2.1 Рабочий процесс ReAct

До появления ReAct господствовавшие методы делились на два типа: «чистое мышление», как в **Chain-of-Thought** — позволяет выполнять сложные логические рассуждения, но не взаимодействует с внешним миром и склонно к фактическим галлюцинациям; и «чистое действие» — модель напрямую выводит действие для исполнения, но лишена планирования и коррекции ошибок.

Гениальность ReAct в том, что он признаёт **взаимодополняемость мышления и действия**: мышление направляет действие, а результаты действия, в свою очередь, корректируют мышление. С этой целью парадигма ReAct использует специальный инженеринг подсказок, направляя модель так, чтобы вывод каждого шага следовал фиксированной траектории:

- **Thought (Мысль):** «Внутренний монолог» агента. Он анализирует текущую ситуацию, декомпозирует задачи, формулирует следующий план или осмысляет результаты предыдущего шага.
- **Action (Действие):** Конкретное действие, которое агент решает предпринять, — как правило, вызов внешнего инструмента, например `Search['последний телефон Huawei']`.
- **Observation (Наблюдение):** Результат, возвращённый внешним инструментом после выполнения `Action`, — например, сводка результатов поиска или ответ API.

Агент непрерывно повторяет цикл **Thought → Action → Observation**, добавляя новые результаты наблюдений в историю — непрерывно расширяющийся контекст — до тех пор, пока в `Thought` не решит, что нашёл финальный ответ, и не выдаст результат. Этот процесс создаёт мощную синергию: **рассуждения делают действия целенаправленными, а действия дают рассуждениям фактическую основу.**

Формально данный процесс можно выразить так, как показано на рисунке 4.1. На каждом временном шаге $t$ политика агента (большая языковая модель $\pi$) генерирует текущую мысль $th_t$ и действие $a_t$ на основе исходного вопроса $q$ и исторической траектории всех предыдущих пар «действие–наблюдение» $((a_1,o_1),\dots,(a_{t-1},o_{t-1}))$:

$$\left(th_t,a_t\right)=\pi\left(q,(a_1,o_1),\ldots,(a_{t-1},o_{t-1})\right)$$

Затем инструмент $T$ в среде исполняет действие $a_t$ и возвращает новый результат наблюдения $o_t$:

$$o_t = T(a_t)$$

Цикл продолжается, добавляя новые пары $(a_t,o_t)$ в историю, пока модель в мысли $th_t$ не определит, что задача выполнена.

Данный механизм особенно подходит для следующих сценариев:

- **Задачи, требующие внешних знаний**: запросы актуальной информации (погода, новости, котировки акций), поиск знаний в специализированных областях и т. д.
- **Задачи, требующие точных вычислений**: делегирование математических задач инструментам-калькуляторам во избежание ошибок вычислений LLM.
- **Задачи взаимодействия с API**: работа с базами данных, вызов API сервиса для выполнения определённых функций.

Поэтому мы построим агент ReAct с возможностью **использования внешних инструментов** для ответа на вопросы, которые LLM не может решить самостоятельно с помощью собственной базы знаний. Например: «Какой последний телефон Huawei и каковы его ключевые преимущества?» Этот вопрос требует от агента понять, что нужно выполнить онлайн-поиск, вызвать инструменты для получения результатов и составить сводный ответ.

### 4.2.2 Определение и реализация инструментов

Если большие языковые модели — это мозг агента, то **инструменты (Tools)** — его «руки и ноги» для взаимодействия с внешним миром. Чтобы парадигма ReAct могла реально решать поставленные задачи, агенту необходима возможность вызывать внешние инструменты.

Для цели, поставленной в этом разделе — ответа на вопрос о «последнем телефоне Huawei», — нужно снабдить агента инструментом веб-поиска. Здесь мы выбираем **SerpApi**: он предоставляет структурированные результаты поиска Google через API и напрямую возвращает «блоки кратких ответов» (answer summary boxes) или точную информацию из графа знаний.

Для начала установите библиотеку:

```bash
pip install google-search-results
```

Также нужно зарегистрироваться на [официальном сайте SerpApi](https://serpapi.com/), получить бесплатный ключ API и добавить его в файл `.env` в корне проекта:

```bash
# файл .env
# ... (сохраните предыдущие настройки LLM)
SERPAPI_API_KEY="YOUR_SERPAPI_API_KEY"
```

Далее определим и будем управлять этим инструментом через код. Сделаем это поэтапно: сначала реализуем ключевую функциональность инструмента, затем создадим универсальный менеджер инструментов.

#### (1) Реализация основной логики инструмента поиска

Хорошо определённый инструмент должен содержать три ключевых элемента:

1. **Имя**: лаконичный уникальный идентификатор для вызова агентом в `Action`, например `Search`.
2. **Описание**: чёткое описание на естественном языке, объясняющее назначение инструмента. **Это наиважнейшая часть всего механизма**, поскольку LLM будет опираться именно на это описание, решая, когда использовать тот или иной инструмент.
3. **Логика выполнения**: функция или метод, фактически решающий задачу.

Наш первый инструмент — функция `search`, принимающая строку запроса и возвращающая результаты поиска.

```python
from serpapi import SerpApiClient

def search(query: str) -> str:
    """
    Практический инструмент веб-поиска на базе SerpApi.
    Интеллектуально разбирает результаты поиска, отдавая приоритет прямым ответам
    или информации из графа знаний.
    """
    print(f"🔍 Выполняется [SerpApi] веб-поиск: {query}")
    try:
        api_key = os.getenv("SERPAPI_API_KEY")
        if not api_key:
            return "Ошибка: SERPAPI_API_KEY не настроен в файле .env."

        params = {
            "engine": "google",
            "q": query,
            "api_key": api_key,
            "gl": "cn",    # код страны
            "hl": "zh-cn", # код языка
        }
        
        client = SerpApiClient(params)
        results = client.get_dict()
        
        # Умный разбор: сначала ищем наиболее прямой ответ
        if "answer_box_list" in results:
            return "\n".join(results["answer_box_list"])
        if "answer_box" in results and "answer" in results["answer_box"]:
            return results["answer_box"]["answer"]
        if "knowledge_graph" in results and "description" in results["knowledge_graph"]:
            return results["knowledge_graph"]["description"]
        if "organic_results" in results and results["organic_results"]:
            # Если прямого ответа нет, возвращаем сводки первых трёх органических результатов
            snippets = [
                f"[{i+1}] {res.get('title', '')}\n{res.get('snippet', '')}"
                for i, res in enumerate(results["organic_results"][:3])
            ]
            return "\n\n".join(snippets)
        
        return f"К сожалению, информация по запросу '{query}' не найдена."

    except Exception as e:
        return f"Ошибка при выполнении поиска: {e}"
```

В приведённом коде сначала проверяется наличие `answer_box` (блок кратких ответов Google) или `knowledge_graph` (граф знаний). Если они есть, сразу возвращаются наиболее точные ответы. В противном случае используется запасной вариант: возвращаются сводки первых трёх обычных результатов поиска. Такой «умный разбор» обеспечивает LLM входными данными более высокого качества.

#### (2) Создание универсального исполнителя инструментов

Когда агенту требуется несколько инструментов (например, помимо поиска — ещё вычисления, запросы к базе данных и т. д.), нужен единый менеджер для их регистрации и диспетчеризации. Для этого создадим класс `ToolExecutor`.

```python
from typing import Dict, Any

class ToolExecutor:
    """
    Исполнитель инструментов, отвечающий за управление и запуск инструментов.
    """
    def __init__(self):
        self.tools: Dict[str, Dict[str, Any]] = {}

    def registerTool(self, name: str, description: str, func: callable):
        """
        Регистрирует новый инструмент в наборе инструментов.
        """
        if name in self.tools:
            print(f"Предупреждение: инструмент '{name}' уже существует и будет перезаписан.")
        self.tools[name] = {"description": description, "func": func}
        print(f"Инструмент '{name}' зарегистрирован.")

    def getTool(self, name: str) -> callable:
        """
        Возвращает функцию-исполнитель инструмента по его имени.
        """
        return self.tools.get(name, {}).get("func")

    def getAvailableTools(self) -> str:
        """
        Возвращает отформатированную строку с описанием всех доступных инструментов.
        """
        return "\n".join([
            f"- {name}: {info['description']}" 
            for name, info in self.tools.items()
        ])
```

#### (3) Тестирование

Теперь зарегистрируем инструмент `search` в `ToolExecutor` и проверим, что весь процесс работает корректно.

```python
# --- Инициализация инструментов и пример использования ---
if __name__ == '__main__':
    # 1. Инициализируем исполнитель инструментов
    toolExecutor = ToolExecutor()

    # 2. Регистрируем практический инструмент поиска
    search_description = "Поисковая система в интернете. Используйте этот инструмент, когда нужно ответить на вопросы о текущих событиях, фактах и информации, отсутствующей в базе знаний."
    toolExecutor.registerTool("Search", search_description, search)

    # 3. Выводим доступные инструменты
    print("\n--- Доступные инструменты ---")
    print(toolExecutor.getAvailableTools())

    # 4. Вызов Action агентом — задаём вопрос о реальном времени
    print("\n--- Выполняем Action: Search['Какая последняя модель GPU NVIDIA'] ---")
    tool_name = "Search"
    tool_input = "Какая последняя модель GPU NVIDIA"

    tool_function = toolExecutor.getTool(tool_name)
    if tool_function:
        observation = tool_function(tool_input)
        print("--- Observation ---")
        print(observation)
    else:
        print(f"Ошибка: инструмент с именем '{tool_name}' не найден.")
```

### 4.2.3 Программная реализация агента ReAct

Теперь соберём все независимые компоненты — LLM-клиент и исполнитель инструментов — и построим полноценный агент ReAct. Основную логику инкапсулируем в класс `ReActAgent`. Для лучшего понимания разобьём реализацию этого класса на несколько ключевых частей.

#### (1) Проектирование системной подсказки

Подсказка — краеугольный камень всего механизма ReAct; она содержит инструкции по работе для большой языковой модели. Нужно тщательно разработать шаблон, который будет динамически подставлять доступные инструменты, вопрос пользователя и историю промежуточных шагов.

```bash
# Шаблон подсказки ReAct
REACT_PROMPT_TEMPLATE = """
Обратите внимание: вы — интеллектуальный ассистент, способный вызывать внешние инструменты.

Доступные инструменты:
{tools}

Пожалуйста, строго придерживайтесь следующего формата ответа:

Thought: Ваш мыслительный процесс — для анализа проблемы, декомпозиции задач, планирования следующего действия или осмысления результатов предыдущего шага.
Action: Действие, которое вы решаете предпринять; должно быть в одном из следующих форматов:
- `{{tool_name}}[{{tool_input}}]`: вызов доступного инструмента.
- `Finish[final answer]`: когда вы считаете, что получили финальный ответ.
- Когда вы собрали достаточно информации для ответа на итоговый вопрос пользователя, после поля Action: необходимо использовать `Finish[final answer]` для вывода финального ответа.

Теперь, пожалуйста, приступите к решению следующей задачи:
Question: {question}
History: {history}
"""
```

Этот шаблон определяет спецификацию взаимодействия агента и LLM:

- **Определение роли**: «Вы — интеллектуальный ассистент, способный вызывать внешние инструменты» задаёт роль LLM.
- **Список инструментов (`{tools}`)**: сообщает LLM, какими «руками и ногами» он располагает.
- **Соглашение о формате (`Thought`/`Action`)**: важнейшая часть — принудительно структурирует вывод LLM, позволяя точно разбирать его намерения с помощью кода.
- **Динамический контекст (`{question}`/`{history}`)**: подставляет исходный вопрос пользователя и постоянно накапливаемую историю взаимодействий, позволяя LLM принимать решения на основе полного контекста.

#### (2) Реализация основного цикла

Ядро `ReActAgent` — цикл, непрерывно выполняющий «форматирование подсказки → вызов LLM → исполнение действия → интеграция результатов» вплоть до выполнения задачи или достижения максимального числа шагов.

```python
class ReActAgent:
    def __init__(self, llm_client: HelloAgentsLLM, tool_executor: ToolExecutor, max_steps: int = 5):
        self.llm_client = llm_client
        self.tool_executor = tool_executor
        self.max_steps = max_steps
        self.history = []

    def run(self, question: str):
        """
        Запускает агент ReAct для ответа на вопрос.
        """
        self.history = []  # Сбрасываем историю перед каждым запуском
        current_step = 0

        while current_step < self.max_steps:
            current_step += 1
            print(f"--- Шаг {current_step} ---")

            # 1. Форматируем подсказку
            tools_desc = self.tool_executor.getAvailableTools()
            history_str = "\n".join(self.history)
            prompt = REACT_PROMPT_TEMPLATE.format(
                tools=tools_desc,
                question=question,
                history=history_str
            )

            # 2. Вызываем LLM для «размышления»
            messages = [{"role": "user", "content": prompt}]
            response_text = self.llm_client.think(messages=messages)

            if not response_text:
                print("Ошибка: LLM не вернул корректный ответ.")
                break

            # ... (Последующие шаги: разбор, исполнение, интеграция)
```

Метод `run` — точка входа агента. Цикл `while` составляет основу парадигмы ReAct, а параметр `max_steps` служит важным предохранительным клапаном, защищающим от бесконечных циклов и истощения ресурсов.

#### (3) Реализация парсера вывода

LLM возвращает простой текст, и нам нужно точно извлечь из него `Thought` и `Action`. Для этого используются вспомогательные функции разбора, как правило на основе регулярных выражений.

```python
# (Эти методы являются частью класса ReActAgent)
    def _parse_output(self, text: str):
        """Разбирает вывод LLM, извлекая Thought и Action.
        """
        # Thought: совпадение до Action: или конца текста
        thought_match = re.search(r"Thought:\s*(.*?)(?=\nAction:|$)", text, re.DOTALL)
        # Action: совпадение до конца текста
        action_match = re.search(r"Action:\s*(.*?)$", text, re.DOTALL)
        thought = thought_match.group(1).strip() if thought_match else None
        action = action_match.group(1).strip() if action_match else None
        return thought, action

    def _parse_action(self, action_text: str):
        """Разбирает строку Action, извлекая имя инструмента и входные данные.
        """
        match = re.match(r"(\w+)\[(.*)\]", action_text, re.DOTALL)
        if match:
            return match.group(1), match.group(2)
        return None, None
```

- `_parse_output`: отвечает за разделение двух основных частей — `Thought` и `Action` — из полного ответа LLM.
- `_parse_action`: выполняет дальнейший разбор строки `Action`, например извлекает имя инструмента `Search` и входные данные `последний телефон Huawei` из строки `Search[последний телефон Huawei]`.

#### (4) Вызов и исполнение инструмента

```python
# (Эта логика находится внутри цикла while метода run)
            # 3. Разбираем вывод LLM
            thought, action = self._parse_output(response_text)

            if thought:
                print(f"Thought: {thought}")

            if not action:
                print("Предупреждение: не удалось разобрать корректный Action; процесс остановлен.")
                break

            # 4. Исполняем Action
            if action.startswith("Finish"):
                # Если это инструкция Finish — извлекаем финальный ответ и завершаем
                final_answer = re.match(r"Finish\[(.*)\]", action).group(1)
                print(f"🎉 Финальный ответ: {final_answer}")
                return final_answer

            tool_name, tool_input = self._parse_action(action)
            if not tool_name or not tool_input:
                # ... Обработка некорректного формата Action ...
                continue

            print(f"🎬 Action: {tool_name}[{tool_input}]")

            tool_function = self.tool_executor.getTool(tool_name)
            if not tool_function:
                observation = f"Ошибка: инструмент с именем '{tool_name}' не найден."
            else:
                observation = tool_function(tool_input)  # Вызываем реальный инструмент
```

Этот код — исполнительный центр `Action`. Сначала проверяется, не является ли это инструкцией `Finish`; если да, процесс завершается. В противном случае через `tool_executor` получается соответствующая функция инструмента и вызывается для получения `observation`.

#### (5) Интеграция результатов наблюдения

Последний шаг — ключ к замыканию цикла — добавление самого `Action` и `Observation` после исполнения инструмента обратно в историю, обеспечивая новый контекст для следующей итерации.

```python
# (Эта логика следует за вызовом инструмента, в конце цикла while)
            print(f"👀 Observation: {observation}")

            # Добавляем Action и Observation этого раунда в историю
            self.history.append(f"Action: {action}")
            self.history.append(f"Observation: {observation}")

        # Цикл завершён
        print("Достигнут предел шагов; процесс остановлен.")
        return None
```

Добавляя `Observation` в `self.history`, агент «видит» результаты предыдущего действия при формировании подсказки в следующем раунде и может строить новые мысли и планы.

### 4.2.4 Характеристики, ограничения и техники отладки ReAct

Реализовав агент ReAct своими руками, мы не только освоили его рабочий процесс, но и должны были глубже разобраться во внутренних механизмах. У любой технической парадигмы есть сильные стороны и области для улучшения — обобщим их для ReAct.

#### (1) Основные характеристики ReAct

1. **Высокая интерпретируемость**: одно из главных преимуществ ReAct — прозрачность. Через цепочку `Thought` мы ясно видим «мыслительный путь» агента на каждом шаге: почему выбран именно этот инструмент и что планируется дальше. Это критически важно для понимания, доверия и отладки поведения агента.
2. **Динамическое планирование и возможность коррекции ошибок**: в отличие от парадигм, генерирующих полный план единовременно, ReAct работает по принципу «шаг за шагом». Он динамически корректирует последующие `Thought` и `Action` на основе `Observation`, получаемых из внешнего мира. Если результаты поиска неудовлетворительны, на следующем шаге можно скорректировать запрос и повторить попытку.
3. **Способность к синергии инструментов**: парадигма ReAct естественным образом объединяет способность LLM к рассуждению и исполнительные возможности внешних инструментов. LLM отвечает за стратегию, инструменты — за решение конкретных задач; они работают синергетически, преодолевая ограничения отдельных LLM по актуальности знаний, точности вычислений и т. д.

#### (2) Присущие ограничения ReAct

1. **Сильная зависимость от собственных возможностей LLM**: успех процесса ReAct во многом определяется комплексными возможностями базового LLM. Если логические способности, способность следовать инструкциям или генерировать форматированный вывод недостаточны, легко получить неверное планирование на этапе `Thought` или инструкции несоответствующего формата на этапе `Action`.
2. **Проблемы эффективности выполнения**: из-за пошагового характера для выполнения задачи обычно требуется несколько вызовов LLM. Каждый вызов сопряжён с сетевой задержкой и вычислительными затратами. Для сложных задач последовательный цикл «думать–действовать» может привести к высокому суммарному времени и стоимости.
3. **Хрупкость подсказок**: стабильная работа всего механизма строится на тщательно разработанном шаблоне подсказки. Любые незначительные изменения в шаблоне, даже разница в формулировках, могут повлиять на поведение LLM. К тому же не все модели способны стабильно следовать заданным форматам.
4. **Риск попадания в локальный оптимум**: пошаговый режим принятия решений означает, что агент лишён глобального, долгосрочного плана. Он может выбрать путь, кажущийся правильным в краткосрочной перспективе, но неоптимальный в долгосрочной, или даже войти в цикл «топтания на месте».

#### (3) Техники отладки

Когда построенный агент ReAct ведёт себя неожиданно, отладку можно вести по следующим направлениям:

- **Проверка полной подсказки**: перед каждым вызовом LLM выводите окончательно сформатированную полную подсказку со всей историей — это наиболее прямой способ отследить источник решений LLM.
- **Анализ необработанного вывода**: при сбое разбора вывода обязательно выведите необработанный текст, возвращённый LLM. Это позволит определить, нарушил ли LLM формат или проблема в логике разбора.
- **Проверка входных и выходных данных инструмента**: убедитесь, что `tool_input`, генерируемый агентом, соответствует формату, ожидаемому функцией инструмента, и что `observation` находится в формате, понятном агенту.
- **Добавление примеров в подсказку (Few-shot Prompting)**: если модель часто ошибается, добавьте один-два полных успешных примера «Thought–Action–Observation» в подсказку для лучшего направления модели.
- **Попробуйте другие модели или параметры**: переход на более мощную модель или корректировка параметра `temperature` (обычно устанавливается равным 0 для детерминированного вывода) иногда напрямую решает проблему.

## 4.3 Plan-and-Solve

Освоив ReAct — реактивную парадигму агента с пошаговым принятием решений, — перейдём к методу совершенно иного стиля, но не менее мощному: **Plan-and-Solve**. Как следует из названия, эта парадигма явно разделяет обработку задачи на два этапа: **сначала план, потом решение**.

Если ReAct подобен опытному детективу, который рассуждает шаг за шагом, опираясь на улики на месте событий (Observation), и в любой момент корректирует направление расследования, то Plan-and-Solve больше похож на архитектора, который перед началом строительства обязательно рисует полный чертёж (план), а затем строго следует ему (выполнение). Кстати, многие инструменты с агентным режимом, которыми мы пользуемся сегодня, воплощают именно этот паттерн проектирования.

### 4.3.1 Принцип работы Plan-and-Solve

Plan-and-Solve Prompting был предложен Лэй Ваном в 2023 году<sup>[2]</sup>. Ключевая мотивация — решить проблему «отклонения от курса» chain-of-thought при работе с многошаговыми сложными задачами.

В отличие от ReAct, объединяющего мышление и действие на каждом шаге, Plan-and-Solve разбивает весь процесс на два ключевых этапа, как показано на рисунке 4.2:

1. **Этап планирования**: получив полный вопрос пользователя, агент первым делом не решает задачу и не вызывает инструменты, а **декомпозирует проблему и составляет чёткий пошаговый план действий**. Сам этот план — продукт вызова LLM.
2. **Этап выполнения**: получив полный план, агент переходит к исполнению. Он **строго следует шагам плана один за другим**. Каждый шаг может представлять собой независимый вызов LLM или обработку результатов предыдущего шага — до тех пор, пока не будут завершены все шаги и получен финальный ответ.

Стратегия «планировать перед действием» позволяет агенту сохранять более высокую согласованность целей при работе со сложными задачами, требующими долгосрочного планирования, и не теряться на промежуточных шагах.

Формально этот двухэтапный процесс можно выразить следующим образом. Сначала модель планирования $\pi_{\text{plan}}$ генерирует план $P = (p_1, p_2, \dots, p_n)$, состоящий из $n$ шагов, на основе исходного вопроса $q$:

$$P = \pi_{\text{plan}}(q)$$

Затем на этапе выполнения модель исполнения $\pi_{\text{solve}}$ выполняет шаги плана по порядку. Для $i$-го шага генерация его решения $s_i$ зависит от исходного вопроса $q$, полного плана $P$ и результатов выполнения всех предыдущих шагов $(s_1, \dots, s_{i-1})$:

$$s_i = \pi_{\text{solve}}(q, P, (s_1, \dots, s_{i-1}))$$

Финальный ответ — результат выполнения последнего шага $s_n$.

Plan-and-Solve особенно подходит для структурированных сложных задач, которые можно чётко декомпозировать, например:

- **Многошаговые текстовые задачи с вычислениями**: сначала нужно составить этапы вычислений, затем решать по порядку.
- **Написание отчётов на основе нескольких источников информации**: сначала планируется структура (введение, источник данных A, источник данных B, выводы), затем контент заполняется поочерёдно.
- **Задачи генерации кода**: сначала разрабатывается структура функций, классов и модулей, затем реализуется поочерёдно.

### 4.3.2 Этап планирования

Чтобы подчеркнуть преимущества парадигмы Plan-and-Solve при структурированных задачах рассуждения, мы не будем использовать инструменты, а выполним задачу рассуждения через проектирование подсказок.

Характерная черта такого типа задач — ответ нельзя получить простым запросом или вычислением; сначала нужно декомпозировать задачу на ряд логически связных подшагов, а затем решать их по порядку. Именно это задействует ключевую возможность Plan-and-Solve — «сначала план, потом исполнение».

**Целевая задача:** «В фруктовом магазине в понедельник продали 15 яблок. Во вторник продали вдвое больше, чем в понедельник. В среду продали на 5 меньше, чем во вторник. Сколько яблок было продано за три дня в целом?»

Задача несложная для LLM, но содержит чёткую логическую цепочку. Для некоторых реальных логических головоломок, если LLM не может получить точный ответ с высоким качеством напрямую, можно воспользоваться этим паттерном проектирования для создания собственного агента. Агенту нужно:

1. **Этап планирования**: декомпозировать задачу на три независимых шага вычисления (вычислить продажи вторника, среды и итоговую сумму).
2. **Этап выполнения**: строго следовать плану, выполнять вычисления пошагово, используя результат каждого шага как входные данные для следующего, и получить итог.

Цель этапа планирования — чтобы LLM получил исходную задачу и вывел чёткий пошаговый план действий. Этот план должен быть структурированным, чтобы наш код мог легко разобрать его и выполнять шаги по очереди. Поэтому проектируемая подсказка должна чётко обозначить роль и задачу модели и привести пример формата вывода.

````python
PLANNER_PROMPT_TEMPLATE = """
Вы — ведущий эксперт по планированию ИИ. Ваша задача — декомпозировать сложные задачи, поставленные пользователями, на план действий, состоящий из нескольких простых шагов.
Убедитесь, что каждый шаг плана является независимой, исполняемой подзадачей и расположен в строгом логическом порядке.
Ваш вывод должен представлять собой список Python, где каждый элемент — строка, описывающая подзадачу.

Вопрос: {question}

Пожалуйста, строго выводите план в следующем формате, с ```python и ``` в качестве обязательных префикса и суффикса:
```python
["Шаг 1", "Шаг 2", "Шаг 3", ...]
```
"""
````

Данная подсказка обеспечивает качество и стабильность вывода через следующие аспекты:
- **Определение роли**: «ведущий эксперт по планированию ИИ» активирует профессиональные возможности модели.
- **Описание задачи**: чётко определяет цель «декомпозиции задачи».
- **Ограничение формата**: принудительно структурирует вывод в виде строки в формате списка Python, что значительно упрощает последующий разбор кодом — более стабильно и надёжно, чем разбор естественного языка.

Далее инкапсулируем логику этой подсказки в класс `Planner` — наш планировщик.

```python
# Предполагается, что класс HelloAgentsLLM в llm_client.py уже определён
# from llm_client import HelloAgentsLLM

class Planner:
    def __init__(self, llm_client):
        self.llm_client = llm_client

    def plan(self, question: str) -> list[str]:
        """
        Генерирует план действий на основе вопроса пользователя.
        """
        prompt = PLANNER_PROMPT_TEMPLATE.format(question=question)

        # Для генерации плана строим простой список сообщений
        messages = [{"role": "user", "content": prompt}]

        print("--- Генерация плана ---")
        # Используем потоковый вывод для получения полного плана
        response_text = self.llm_client.think(messages=messages) or ""

        print(f"✅ План сгенерирован:\n{response_text}")

        # Разбираем строку-список, выведенную LLM
        try:
            # Находим содержимое между ```python и ```
            plan_str = response_text.split("```python")[1].split("```")[0].strip()
            # Используем ast.literal_eval для безопасного выполнения строки и преобразования в список Python
            plan = ast.literal_eval(plan_str)
            return plan if isinstance(plan, list) else []
        except (ValueError, SyntaxError, IndexError) as e:
            print(f"❌ Ошибка при разборе плана: {e}")
            print(f"Исходный ответ: {response_text}")
            return []
        except Exception as e:
            print(f"❌ Неизвестная ошибка при разборе плана: {e}")
            return []
```

### 4.3.3 Исполнитель и управление состоянием

После того как планировщик (`Planner`) создаёт чёткий план действий, нам нужен исполнитель (`Executor`) для последовательного выполнения задач плана. Исполнитель не только отвечает за вызов LLM для решения каждой подзадачи, но и играет ключевую роль в **управлении состоянием**: он должен фиксировать результаты выполнения каждого шага и предоставлять их как контекст для последующих шагов, обеспечивая плавную передачу информации по всей цепочке задач.

Подсказка исполнителя отличается от подсказки планировщика. Её цель — не декомпозиция задачи, а **сосредоточение на решении текущего шага на основе имеющегося контекста**. Поэтому подсказка должна включать следующую ключевую информацию:

- **Исходный вопрос**: чтобы модель всегда понимала конечную цель.
- **Полный план**: чтобы модель понимала место текущего шага в общей задаче.
- **Предыдущие шаги и результаты**: предоставляет уже выполненную работу как прямые входные данные для текущего шага.
- **Текущий шаг**: чётко указывает модели, какую конкретную задачу ей нужно решить сейчас.

```python
EXECUTOR_PROMPT_TEMPLATE = """
Вы — ведущий исполнительный эксперт ИИ. Ваша задача — строго следовать заданному плану и решать проблему шаг за шагом.
Вы получите исходный вопрос, полный план и уже выполненные шаги с результатами.
Пожалуйста, сосредоточьтесь на решении «текущего шага» и выводите только финальный ответ на этот шаг, без каких-либо дополнительных объяснений.

# Исходный вопрос:
{question}

# Полный план:
{plan}

# Предыдущие шаги и результаты:
{history}

# Текущий шаг:
{current_step}

Пожалуйста, выведите только ответ на «текущий шаг»:
"""
```

Инкапсулируем логику выполнения в класс `Executor`. Этот класс будет обходить план в цикле, вызывать LLM и поддерживать историю (состояние).

```python
class Executor:
    def __init__(self, llm_client):
        self.llm_client = llm_client

    def execute(self, question: str, plan: list[str]) -> str:
        """
        Выполняет план пошагово и решает задачу.
        """
        history = ""  # Строка для хранения предыдущих шагов и результатов

        print("\n--- Выполнение плана ---")

        for i, step in enumerate(plan):
            print(f"\n-> Выполняем шаг {i+1}/{len(plan)}: {step}")

            prompt = EXECUTOR_PROMPT_TEMPLATE.format(
                question=question,
                plan=plan,
                history=history if history else "Нет",  # Для первого шага история пуста
                current_step=step
            )

            messages = [{"role": "user", "content": prompt}]

            response_text = self.llm_client.think(messages=messages) or ""

            # Обновляем историю для следующего шага
            history += f"Шаг {i+1}: {step}\nРезультат: {response_text}\n\n"

            print(f"✅ Шаг {i+1} завершён, результат: {response_text}")

        # После завершения цикла ответ последнего шага является финальным ответом
        final_answer = response_text
        return final_answer
```

Теперь у нас есть отдельно построенные `Planner`, отвечающий за «планирование», и `Executor`, отвечающий за «выполнение». Последний шаг — объединить эти два компонента в единый агент `PlanAndSolveAgent` и дать ему полные возможности для решения задач. Создадим главный класс `PlanAndSolveAgent`, чья ответственность предельно ясна: получить LLM-клиент, инициализировать внутренние планировщик и исполнитель, и предоставить простой метод `run` для запуска всего процесса.

```python
class PlanAndSolveAgent:
    def __init__(self, llm_client):
        """
        Инициализирует агента и создаёт экземпляры планировщика и исполнителя.
        """
        self.llm_client = llm_client
        self.planner = Planner(self.llm_client)
        self.executor = Executor(self.llm_client)

    def run(self, question: str):
        """
        Запускает полный процесс агента: сначала план, затем выполнение.
        """
        print(f"\n--- Начало обработки вопроса ---\nВопрос: {question}")

        # 1. Вызываем планировщик для генерации плана
        plan = self.planner.plan(question)

        # Проверяем, успешно ли сгенерирован план
        if not plan:
            print("\n--- Задача прервана --- \nНе удалось сгенерировать корректный план действий.")
            return

        # 2. Вызываем исполнитель для выполнения плана
        final_answer = self.executor.execute(question, plan)

        print(f"\n--- Задача выполнена ---\nФинальный ответ: {final_answer}")
```

Проектирование класса `PlanAndSolveAgent` воплощает принцип «композиция вместо наследования»: он не содержит сложной логики сам по себе, а выступает оркестратором, чётко вызывающим внутренние компоненты для выполнения задач.

## 4.4 Рефлексия (Reflection)

В уже реализованных нами парадигмах ReAct и Plan-and-Solve рабочий процесс агента завершается сразу после выполнения задачи. Однако первоначальные ответы, которые они генерируют — будь то траектории действий или финальные результаты — могут содержать ошибки или требовать улучшений. Основная идея механизма **рефлексии (Reflection)** заключается во введении для агента **петли обратной связи для пост-исправления ошибок (самокоррекции)**. Это позволяет ему оценивать собственную работу, выявлять недостатки и итеративно оптимизировать результат, подобно тому, как это делают люди.

### 4.4.1 Ядро механизма рефлексии

Источником вдохновения для механизма рефлексии служит процесс обучения человека: мы вычитываем текст после написания первого черновика и перепроверяем решение математической задачи. Эта концепция нашла отражение во многих исследованиях, например во фреймворке *Reflexion*, предложенном Ноа Шинном (Noah Shinn) в 2023 году<sup>[3]</sup>. Базовый рабочий процесс можно представить в виде лаконичного трехэтапного цикла: **Выполнение (Execute) $\rightarrow$ Рефлексия (Reflect) $\rightarrow$ Оптимизация (Refine)**.

1. **Выполнение (Execution)**: Сначала агент пытается решить задачу с помощью привычных методов (таких как ReAct или Plan-and-Solve), создавая предварительное решение или траекторию действий. Это можно назвать «первым черновиком».
2. **Рефлексия (Reflection)**: Далее агент переходит к фазе критического анализа. Он вызывает отдельный экземпляр большой языковой модели (или ту же модель со специальными подсказками), которая выступает в роли «рецензента» (reviewer). Этот «рецензент» оценивает «первый черновик» по нескольким направлениям:
   - **Фактические ошибки**: Противоречит ли содержание здравому смыслу или известным фактам?
   - **Логические изъяны**: Есть ли несогласованность или противоречия в процессе рассуждения?
   - **Вопросы эффективности**: Существует ли более прямой и лаконичный путь решения задачи?
   - **Неполнота информации**: Не упущены ли какие-то важные ограничения или аспекты проблемы? На основе этой оценки формируется структурированный **отзыв (Feedback)** с указанием конкретных проблем и предложений по улучшению.
3. **Оптимизация (Refinement)**: Наконец, агент использует «первый черновик» и полученный «отзыв» в качестве нового контекста, снова обращается к большой языковой модели и просит её скорректировать первую версию на основе замечаний рецензента, создавая более качественный «исправленный вариант».

Как показано на рисунке 4.3, этот цикл может повторяться несколько раз до тех пор, пока на этапе рефлексии больше не будет выявляться новых проблем или пока не будет достигнут установленный лимит итераций. Мы можем формально выразить этот процесс оптимизации. Предположим, что $O_i$ — это результат, полученный на итерации $i$ (где $O_0$ — первоначальный ответ). Тогда модель рефлексии $\pi_{\text{reflect}}$ генерирует отзыв $F_i$ для $O_i$:

$$
F_i = \pi_{\text{reflect}}(\text{Task}, O_i)
$$

Затем модель оптимизации $\pi_{\text{refine}}$ объединяет исходное задание, предыдущую версию ответа и отзыв для генерации новой версии ответа $O_{i+1}$:

$$
O_{i+1} = \pi_{\text{refine}}(\text{Task}, O_i, F_i)
$$

По сравнению с двумя предыдущими парадигмами ценность рефлексии заключается в следующем:
- Она дает агенту внутренний цикл исправления ошибок, благодаря чему он больше не зависит полностью от внешней обратной связи от инструментов (`Observation` в ReAct) и может исправлять высокоуровневые логические и стратегические ошибки.
- Она превращает разовое выполнение задачи в процесс непрерывной оптимизации, что существенно повышает итоговую долю успешных решений и качество ответов на сложные задачи.
- Она формирует для агента временную **«краткосрочную память»**. Вся траектория «выполнение–рефлексия–улучшение» образует ценную хронологию опыта; агент не просто знает правильный ответ, но и помнит, как именно он пришел к нему от несовершенного первого черновика. Более того, такая система памяти может быть **мультимодальной**, позволяя агенту анализировать и дорабатывать результаты, отличные от текста (например, код, изображения и т. д.), что закладывает основу для создания более мощных мультимодальных агентов.

### 4.4.2 Постановка задачи и проектирование модуля памяти

Чтобы реализовать механизм рефлексии на практике, нам потребуется ввести механизм управления памятью, поскольку рефлексия неразрывно связана с сохранением и извлечением информации. Если контекст становится слишком длинным, предоставление рецензенту всей информации напрямую может привести к избыточности. В этом практическом руководстве мы сосредоточимся на **генерации кода и его итеративной оптимизации**.

Практическая задача для этого шага звучит так: **«Напишите функцию на Python для поиска всех простых чисел от 1 до n»**.

Эта задача отлично подходит для демонстрации механизма рефлексии по следующим причинам:
1. **Наличие очевидного пути оптимизации**: Код, изначально созданный языковой моделью, скорее всего, будет представлять собой простую переборную проверку делителей (метод пробных делений), которая работает медленно.
2. **Четкие точки для рефлексии**: Анализируя такой код, рецензент легко обнаружит проблемы вроде «слишком высокой временной сложности» или «избыточных вычислений».
3. **Понятное направление улучшения**: Опираясь на замечания, модель может оптимизировать алгоритм до эффективного решета Эратосфена или версии с мемоизацией.

Суть рефлексии — в итерациях, а залог успешных итераций — способность запоминать прошлые попытки и полученный фидбек. Поэтому для реализации этой парадигмы необходим модуль «краткосрочной памяти». Он будет сохранять полную траекторию каждого цикла «выполнение–рефлексия».

```python
from typing import List, Dict, Any, Optional

class Memory:
    """
    Простой модуль краткосрочной памяти для хранения действий агента и траектории рефлексии.
    """

    def __init__(self):
        """
        Инициализирует пустой список для хранения записей.
        """
        self.records: List[Dict[str, Any]] = []

    def add_record(self, record_type: str, content: str):
        """
        Добавляет новую запись в память.

        Параметры:
        - record_type (str): Тип записи ('execution' или 'reflection').
        - content (str): Конкретное содержимое записи (например, сгенерированный код или отзыв рефлексии).
        """
        record = {"type": record_type, "content": content}
        self.records.append(record)
        print(f"📝 Память обновлена, добавлена запись типа '{record_type}'.")

    def get_trajectory(self) -> str:
        """
        Форматирует все записи памяти в связный текстовый сегмент для построения промптов.
        """
        trajectory_parts = []
        for record in self.records:
            if record['type'] == 'execution':
                trajectory_parts.append(f"--- Предыдущая попытка (код) ---\n{record['content']}")
            elif record['type'] == 'reflection':
                trajectory_parts.append(f"--- Отзыв рецензента ---\n{record['content']}")

        return "\n\n".join(trajectory_parts)

    def get_last_execution(self) -> Optional[str]:
        """
        Возвращает самый последний результат выполнения (например, последний сгенерированный код).
        Возвращает None, если записей о выполнении нет.
        """
        for record in reversed(self.records):
            if record['type'] == 'execution':
                return record['content']
        return None
```

Конструкция этого класса `Memory` достаточно проста:
- Список `records` используется для последовательного хранения данных о действиях и рефлексии.
- Метод `add_record` отвечает за добавление новых элементов.
- Метод `get_trajectory` является ключевым: он «сериализует» историю памяти в текстовый блок, который можно вставить в промпт на следующем шаге, предоставляя модели полный контекст её предыдущей работы.
- Метод `get_last_execution` позволяет удобно извлечь последнюю рабочую версию кода («черновик») для ревью.

### 4.4.3 Программная реализация Reflection-агента

Используя модуль `Memory` в качестве фундамента, мы можем перейти к построению основной логики `ReflectionAgent`. Рабочий процесс агента строится вокруг итеративного цикла «выполнение–рефлексия–улучшение» и управляет большой языковой моделью через систему ролевых промптов.

#### (1) Проектирование системных подсказок (промптов)

В отличие от предыдущих парадигм, механизму рефлексии требуется несколько специализированных промптов для разных ролей, работающих совместно:

1. **Промпт первоначального выполнения (Initial Execution Prompt)**: Обычный промпт для первой попытки написания кода, требующий от модели просто решить задачу.

```python
INITIAL_PROMPT_TEMPLATE = """
Вы — опытный Python-программист. Пожалуйста, напишите функцию на Python в соответствии со следующими требованиями.
Ваш код должен содержать полную сигнатуру функции, docstring и соответствовать стандартам кодирования PEP 8.

Требование: {task}

Пожалуйста, выводите только код напрямую, без каких-либо дополнительных объяснений.
"""
```

2. **Промпт рефлексии (Reflection Prompt)**: Ядро всего процесса. Он задает модели роль беспристрастного ревьюера, требуя критически проанализировать ранее сгенерированный код и предоставить четкие, практически применимые замечания.

````python
REFLECT_PROMPT_TEMPLATE = """
Вы — чрезвычайно строгий эксперт по код-ревью и опытный инженер-алгоритмист, предъявляющий высочайшие требования к производительности кода.
Ваша задача — проанализировать следующий код на Python и сфокусироваться на поиске его основного узкого места с точки зрения **эффективности алгоритма**.

# Исходное задание:
{task}

# Код для проверки:
```python
{code}
```

Пожалуйста, проанализируйте временную сложность этого кода и подумайте, существует ли **алгоритмически более совершенное** решение для значительного повышения производительности.
Если такое решение есть, четко укажите на недостатки текущего алгоритма и предложите конкретные, выполнимые рекомендации по улучшению (например, использование метода решета вместо деления на потенциальные делители).
Только если код уже достиг оптимального уровня с точки зрения алгоритма, вы можете ответить "no improvement needed" (улучшение не требуется).

Пожалуйста, выводите свой отзыв напрямую, без каких-либо дополнительных объяснений.
"""
````

3. **Промпт оптимизации (Refinement Prompt)**: Этот промпт направляет модель на исправление кода с учетом замечаний ревьюера.

```python
REFINE_PROMPT_TEMPLATE = """
Вы — опытный Python-программист. Вы оптимизируете свой код на основе отзыва эксперта по код-ревью.

# Исходное задание:
{task}

# Ваша предыдущая версия кода:
{last_code_attempt}

# Отзыв рецензента:
{feedback}

Пожалуйста, сгенерируйте новую оптимизированную версию кода на основе отзыва рецензента.
Ваш код должен содержать полную сигнатуру функции, docstring и соответствовать стандартам кодирования PEP 8.
Пожалуйста, выводите оптимизированный код напрямую, без каких-либо дополнительных объяснений.
"""
```

#### (2) Создание класса агента

Теперь объединим модули промптов и класс `Memory` в классе `ReflectionAgent`.

```python
# Предполагается, что в llm_client.py и memory.py уже объявлены соответствующие классы
# from llm_client import HelloAgentsLLM
# from memory import Memory

class ReflectionAgent:
    def __init__(self, llm_client: HelloAgentsLLM, max_iterations: int = 3):
        self.llm_client = llm_client
        self.memory = Memory()
        self.max_iterations = max_iterations

    def run(self, task: str):
        print(f"\n--- Начало обработки задачи ---\nЗадача: {task}")

        # --- 1. Первоначальное выполнение ---
        print("\n--- Выполнение первоначальной попытки ---")
        initial_prompt = INITIAL_PROMPT_TEMPLATE.format(task=task)
        initial_code = self._get_llm_response(initial_prompt)
        self.memory.add_record("execution", initial_code)

        # --- 2. Цикл итераций: рефлексия и оптимизация ---
        for i in range(self.max_iterations):
            print(f"\n--- Итерация {i+1}/{self.max_iterations} ---")

            # а. Рефлексия (код-ревью)
            print("\n-> Выполнение рефлексии...")
            last_code = self.memory.get_last_execution()
            reflect_prompt = REFLECT_PROMPT_TEMPLATE.format(task=task, code=last_code)
            feedback = self._get_llm_response(reflect_prompt)
            self.memory.add_record("reflection", feedback)

            # б. Проверка условия завершения
            if "no improvement needed" in feedback.lower() or "улучшение не требуется" in feedback.lower() or "无需改进" in feedback:
                print("\n✅ Рефлексия считает, что код не требует улучшений, задача выполнена.")
                break

            # в. Оптимизация (исправление по фидбеку)
            print("\n-> Выполнение оптимизации...")
            refine_prompt = REFINE_PROMPT_TEMPLATE.format(
                task=task,
                last_code_attempt=last_code,
                feedback=feedback
            )
            refined_code = self._get_llm_response(refine_prompt)
            self.memory.add_record("execution", refined_code)

        final_code = self.memory.get_last_execution()
        print(f"\n--- Задача выполнена ---\nИтоговый сгенерированный код:\n```python\n{final_code}\n```")
        return final_code

    def _get_llm_response(self, prompt: str) -> str:
        """Вспомогательный метод для вызова LLM и получения полного потового ответа."""
        messages = [{"role": "user", "content": prompt}]
        response_text = self.llm_client.think(messages=messages) or ""
        return response_text
```

````bash
def find_primes(n):
    """
    Находит все простые числа в диапазоне от 1 до n с помощью алгоритма Решета Эратосфена.

    :param n: Верхняя граница диапазона поиска.
    :return: Список всех найденных простых чисел.
    """
    if n < 2:
        return []

    is_prime = [True] * (n + 1)
    is_prime[0] = is_prime[1] = False

    p = 2
    while p * p <= n:
        if is_prime[p]:
            for i in range(p * p, n + 1, p):
                is_prime[i] = False
        p += 1

    primes = [num for num in range(2, n + 1) if is_prime[num]]
    return primes
````

3. **Сходимость и завершение цикла**: Во втором раунде рефлексии рецензент признал текущее решение высокоэффективным и выдал вердикт «улучшение не требуется». Это условие сработало как триггер завершения программы, обеспечив сходимость процесса.

### 4.4.5 Анализ затрат и результатов механизма рефлексии

Хотя рефлексия отлично справляется с повышением качества решений задач, эти возможности имеют свою цену. В практических сценариях необходимо сопоставлять преимущества, которые она приносит, с сопутствующими затратами.

#### (1) Основные затраты

1. **Дополнительные вызовы языковой модели**: Это самая очевидная статья расходов. Каждая итерация требует как минимум двух дополнительных запросов к LLM (один для рефлексии, второй для исправления). При большом количестве итераций расходы на API и вычислительные ресурсы растут пропорционально.
2. **Увеличение задержки (Latency)**: Рефлексия является строго последовательным процессом; шаг оптимизации не может начаться до завершения код-ревью. Это существенно увеличивает общее время выполнения задачи, что делает подход неприменимым в системах реального времени.
3. **Сложность проектирования промптов (Prompt Engineering)**: Как показал наш пример, стабильность рефлексии зависит от качества промптов. Разработка и отладка промптов под три разные роли («исполнитель», «рецензент», «оптимизатор») требует дополнительных усилий со стороны инженера.

#### (2) Ключевые преимущества

1. **Качественный скачок решений**: Главный плюс рефлексии в том, что она способна превратить «удовлетворительную» первую версию решения в «образцовую» итоговую версию. Переход от работоспособного кода к высокопроизводительному, от поверхностных рассуждений к строгой логике критически важен во многих сферах.
2. **Повышенная надежность и отказоустойчивость**: Внутренние циклы самокоррекции позволяют выявить и исправить логические нестыковки, ложные утверждения или неверную обработку граничных случаев, что повышает предсказуемость работы системы.

Таким образом, механизм рефлексии представляет собой классический пример компромисса **«ресурсы в обмен на качество»**. Он идеально подходит для сценариев с **высокими требованиями к качеству, точности и надежности результатов, при относительно некритичном времени выполнения**. Примеры использования:
- Генерация критически важного программного кода или технических отчетов.
- Выполнение сложного логического вывода в научных исследованиях.
- Системы поддержки принятия решений, требующие глубокого анализа.

И наоборот, если приложению требуется мгновенный отклик или вполне достаточно получить «в целом правильный» ответ, использование более легких парадигм ReAct или Plan-and-Solve окажется более экономически оправданным решением.

## 4.5 Резюме главы

В этой главе, опираясь на знания о больших языковых моделях из Главы 3, мы самостоятельно «изобрели велосипед» — с нуля запрограммировали три классические парадигмы проектирования агентов: ReAct, Plan-and-Solve и Reflection. Мы не только изучили их внутреннее устройство, но и на конкретных практических примерах сравнили их сильные стороны, ограничения и области применения.

**Краткое повторение пройденного:**

1. **ReAct**: Мы создали агента, способного взаимодействовать с внешним миром. В динамическом цикле «мыслю–действую–наблюдаю» он успешно задействовал поисковую систему для ответа на вопросы о недавних событиях, выходящих за рамки его знаний. Его ключевые достоинства — **адаптивность к внешней среде** и **возможность динамического исправления ошибок**, что делает его основным выбором для задач, требующих активного обращения к инструментам.
2. **Plan-and-Solve**: Мы реализовали агента, который сначала формирует план, а затем приступает к его выполнению. Эта парадигма помогла нам решить текстовую математическую задачу, требующую последовательного вывода. Её сила — в **структурированности** и **стабильности**, она незаменима для решения задач с четким логическим путем и глубокими внутренними рассуждениями.
3. **Reflection (саморефлексия)**: Мы построили самообучающегося агента с циклом «выполнение–рефлексия–улучшение», который сумел оптимизировать неэффективную переборную функцию до быстрого алгоритма. Главная ценность парадигмы — **радикальное повышение качества результатов**, что критически важно в проектах с высокими требованиями к точности ответов.

Три рассмотренные парадигмы предлагают разные стратегии решения проблем, резюмированные в таблице 4.1. Выбор конкретного подхода в реальных задачах зависит от приоритетов вашего приложения:

### Таблица 4.1 Стратегия выбора архитектуры цикла агента

| Если ваша задача...                                                               | Рекомендуемый выбор | Ключевое обоснование                                                                                      |
|-----------------------------------------------------------------------------------|---------------------|-----------------------------------------------------------------------------------------------------------|
| Полная неопределенности, требует взаимодействия с внешними API или веб-страницами | **ReAct**           | Он может динамически корректировать путь на основе обратной связи в реальном времени.                     |
| Логический путь ясен, упор на внутренние рассуждения и разбиение на шаги          | **Plan-and-Solve**  | Он обеспечивает стабильный и структурированный рабочий процесс.                                           |
| Крайне высокие требования к качеству и надежности конечного результата            | **Reflection**      | Благодаря итеративной оптимизации он способен превратить «удовлетворительный» ответ в «образцовый».       |

К этому моменту мы освоили фундамент проектирования автономных агентов. В следующей части мы рассмотрим, как применять современные low-code платформы и готовые легковесные библиотеки для ускорения разработки и масштабирования наших ИИ-агентов.
